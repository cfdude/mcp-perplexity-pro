# Design

## Context

See `proposal.md` for motivation and `specs/` for requirements. State that shapes the approach:

- Foundation, usage-log and agent-api are archived (2026-10-09). The server has a client (`client.py`: `request_json` with the create-POST retry rules, `_parse`, redacted `PerplexityError` with `api_message`), the closed eleven-value error vocabulary, a unit of work, project resolution and a recorder (`usage.py: record_usage`, `computed_usage`, `format_usd`) whose caller contract is `CLAUDE.md` "How to record usage". `pricing.search_cost_nano(requests, search_type)` already exists and is pinned to the documented price table (`"standard"` $5/1k, `"fast"` $1/1k). No Search parser is registered in `usage._PARSERS`, and none is needed: the response carries no usage.
- The recorder's production call sites today are `agent.run_costed` (two `record_usage(` lines) and `agent.observe_job_locked` (one), pinned by `tests/test_contract_checks.py::test_record_usage_is_called_from_exactly_two_functions_and_defined_once`.
- The Search API was probed live on 2026-10-09 (spend about $0.044 over 32 billed requests, plus 120 free parallel invalid requests that left no fixture; two more captures, `search_omitted_search_type_accepted` and `search_unknown_field_accepted`, were added after Gate 1 for about $0.006). The captures are committed as `tests/fixtures/search_*.json` with sidecars (`63dcb0f`, `86a6502`): 36 files, of which 20 are 200 responses holding 68 results. Facts below say whether a fixture backs them; "probe only" means observed in the probe, no fixture. Every spec scenario that names "the recorded ..." uses one of them through `httpx2.MockTransport`. Lesson `docs-lie-probe-the-api-first`: the documentation was wrong or silent on eleven points (see "Observed shapes").
- Third-party text, validators: `search.py` imports `check_text`, `_bad`, `_int_in`, `_strict_date`, `_domains`, `_COUNTRY`, `MAX_DOMAINS`, `MAX_DOMAIN_CHARS` and `DATE_CAP` from `agent.py` instead of copying them (one definition of the domain, date and integer rules; moving them to a shared module is a later refactor that would touch the Agent tests). Where Search differs it passes its own bound: `check_text("query", q, 8192)`, `_int_in("max_results", n, 1, 20)` (the Agent `max_results` is 1 to 50; Search stops at 20, `search_max_results_21_400`).
- Tool modules must not use `from __future__ import annotations`; every tool is `register(server)`, typed with `Annotated[..., Field(description=...)]`, returns `ToolResult(content=..., structured_content=...)` and raises `PerplexityError` for anticipated failures.
- The live server runs under pm2 on port 8102 and must not be touched by development or tests; the live acceptance (group 6) is the one place a human restarts it.

## Goals / Non-Goals

**Goals:**
- One cheap-by-default tool that returns ranked web results as structured data, with every filter the API offers for the two cheap search types.
- Every request recorded exactly once through the existing recorder, in the contract's order, without a third hand-written copy of the sequence.
- Local validation of every input the probe showed the API accepts wrongly, bills for nothing, or reports misleadingly.
- Honest output: no attribution the API does not give, no cost the API did not report presented as reported.

**Non-Goals:**
- `people` search (price undocumented, returns individuals' professional data), page snippets (D12), contextualized content extraction, search as an Agent tool, result caching, streaming, pagination beyond `max_results`, a cost ceiling or per-minute throttle, surfacing the rate-limit headers.
- A Search usage parser (D5): nothing to parse until the API reports usage.

## Decisions

**D1. One tool, three new modules and one shared helper.** The name is fixed by the product intent: `perplexity_search`. Layout: `models/search.py` (`SearchResult`, `SearchResponse`), `search.py` (option validation, request building, digestion, `run_search`), `costed.py` (the shared costed-call sequence, D6), `tools/search.py`. Annotations: `readOnlyHint` false (it writes a usage event and may create a project), `destructiveHint` false, `openWorldHint` true, like `perplexity_ask`. One tool with a `query` that is a string or a list, not a `perplexity_multi_search`: the two differ in one argument and one billing fact, and a second schema would cost every session's context twice (D10). *Alternative:* extend `perplexity_ask` with a no-LLM mode. Rejected: different output shape, different cost model, different failure modes.

**D2. Request building is one pure function** (`search.build_request(options)`), tested against the recorded request shapes (each sidecar carries its `request`). Rules and the probe evidence behind each:

| Rule | Evidence |
|---|---|
| Filters are TOP-LEVEL fields (`search_domain_filter`, `search_recency_filter`, `search_after_date_filter`, `search_before_date_filter`, `last_updated_after_filter`, `last_updated_before_filter`, `search_language_filter`, `country`, `max_results`, `max_tokens`, `max_tokens_per_page`), unlike the Agent API where they sit inside a tool's `filters` | every `search_*` sidecar; OpenAPI `ApiSearchRequest` |
| `search_type` is ALWAYS sent (`fast` by default) | `search_omitted_search_type_accepted` shows an omitted type is accepted and answers like any other 200; the response does not say which type ran, so that it ran as standard ($0.005) rests on the documented default and the probe, not on a fixture. Only an explicit `fast` is known to be the cheap one |
| `search_type` is `fast` or `web`; `people` refused | API enum is web, fast, people (`search_bad_search_type_400`); `people` price is undocumented and the result type is personal data |
| `query` is a string or 1 to 5 strings, each non-blank, at most 8192 characters | `search_too_many_queries_400` (`maximum 5 queries allowed, got 6`), `search_empty_query_400` (`query 1 length must be between 1 and 8192 characters, got 0`), `search_missing_query_400` (empty list: `query is required`); a whitespace-only query was a 200 with `results: []` (`search_whitespace_query_empty`), which the docs bill, so it is refused locally (`check_text` refuses it) |
| `max_results` 1 to 20 | `search_max_results_21_400` and `_0_400` (`max results must be between 1 and 20`; both fixtures are fast requests, so "for web alike" is probe only); the OpenAPI schema says maximum 50 (people only); `perplexity_ask`'s own `max_results` stays 1 to 50 |
| Dates: `YYYY-MM-DD` in, `MM/DD/YYYY` out, strict, order checked; output built as `f"{d.month:02d}/{d.day:02d}/{d.year:04d}"`, not `strftime` (whose `%Y` is platform-dependent below year 1000; the Agent path keeps its own `strftime`, untouched) | `search_bad_date_iso_400` (the API refuses ISO, unlike the Agent API, which accepted it); `9/1/2026` (no padding) was accepted; `13/45/2026` refused with the same message; both bounds are inclusive (`search_fast_date_range_inclusive`: results dated 2026-09-01 and 2026-10-01 came back for 09/01 to 10/01) |
| Recency alone, never with any date option | `search_recency_with_dates_400` (clear API message for publication dates); but recency with `last_updated_after_filter` was ACCEPTED (`search_fast_recency_with_updated_accepted`) although the docs say recency cannot combine with any date filter. The effect of that combination is unobserved (whether both filters applied cannot be told from ten results), so it is refused locally on the documented rule. Relaxing it is one scenario and one branch |
| Domains: at most 20, each at most 253 characters, no empty or `-` or whitespace entry, no mixing; an empty list means not given (the Agent path tests `if options.domains`) and is not sent | `search_domains_21_400` (`search domain filter must be at most 20`), OpenAPI `maxLength` 253; a mixed list was ACCEPTED and the response equals the allowlist-only response (`search_fast_mixed_domains_accepted` against `search_fast_allow_domain`), so the deny entry is silently ignored: that is not a result the caller asked for |
| Languages: at most 20, each two lowercase ASCII letters; an empty list means not given | `search_language_21_400` (`cannot have more than 20 languages`); 11 codes accepted (`search_fast_language_11_accepted`) although the prose says 10; `["EN"]` accepted (`search_fast_language_uppercase_accepted`) although the docs say lowercase only; `xx` and `eng` refused by the API as `invalid_language_code` (`search_bad_language_400`), which stays the API's job: this server holds no ISO list |
| Country: two ASCII letters, sent upper case | `ZZ` and `USA` refused by the API as `invalid_country_code` (`search_bad_country_400`); `us` accepted. Validity of the code stays the API's job |
| `max_tokens` 1 to 16384 and `max_tokens_per_page` 1 to 4096 | the API accepts 1 to 1000000 (`search_max_tokens_0_400`). The tighter bounds are this server's own caps, borrowed from the documented ranges of the CLI's `content snippets` command (16384 and 4096), so one call cannot pull a million tokens of web text into the caller's context; labelled as such in the spec. A per-page budget above the total was accepted (`search_fast_page_tokens_above_total`) so no cross-check is made |
| Nothing else is sent | an unknown field (`bogus_param`) was accepted (`search_unknown_field_accepted`; a 200, so billed on the documented rule), so a typo would otherwise be silent |

**How the request tests compare.** Each recorded request the tool accepts is rebuilt from the options that produce it and compared with the sidecar's `request` exactly (the tool's option names differ from the API's field names, so the test carries a small table from sidecar field to option). Exactly six of the 20 recorded 200 requests are NOT reproduced, and the test names them: `search_fast_mixed_domains_accepted`, `search_fast_language_uppercase_accepted`, `search_fast_recency_with_updated_accepted` and `search_whitespace_query_empty` are refused locally; `search_omitted_search_type_accepted` is built with `search_type` `fast` added; `search_unknown_field_accepted` has no option that produces its `bogus_param`. A test fails if a 200 fixture is neither compared nor in that list. Shapes with no sidecar (the minimal request, a combination) are asserted from inline expected dicts labelled as having no recording behind them.

**D3. Several queries come back merged, and the tool says so.** A request with three queries returned ONE flat `results` list (`search_fast_multi_query`: ten results for `max_results` 10, from `rust borrow checker`, `golang generics` and `zig comptime`), with no field naming the query, no grouping and no per-query rank; `max_results` is a total across the queries, not per query. The same query sent twice returned one list of four distinct urls (`search_fast_multi_query_duplicate`): the API de-duplicates urls, the tool does not touch the list. The documentation says each query is "processed independently", which is true of the work and not of the output. The tool therefore cannot attribute results to queries, and does not pretend to: it returns the API's list unchanged, sets `query_count`, adds one warning, and the description says that a caller who needs per-query results makes one call per query. Billing: one unit per request (documented); rate limit: probably one unit per query (`search_fast_multi_query` reads `x-ratelimit-used` 3 for three queries against 1 for `search_fast_single`, limit 50; the two-query `search_fast_multi_query_duplicate` reads 5, so its window was shared with earlier calls and says nothing alone), so a five-query request may be five times closer to a 429 than a single query but costs the same as one.

**D4. Result digestion is one function** (`search.digest(response, secrets, *, max_results, max_tokens, query_count, search_type)`; it never raises). The client keeps `results` as a raw list (D7), so the digest owns every judgment about a result. For each item in the API's order: a non-object, or an object whose `url` is missing, null, not a string or empty, is dropped (a pointer to nowhere is not a result; the digest decides, the tolerant model keeps it); otherwise it maps to `{title, url, snippet, date, last_updated}` where a `title` or `snippet` that is not a string becomes `""` and a `date` or `last_updated` that is not a string becomes `None` (an absent key is `None`). `count` is the number kept, and one warning counts the dropped items. The snippet is the API's page excerpt. Evidence, from the 20 committed 200 responses (68 results): `date` is absent (not null) on 22 of 68 (32%), `last_updated` is present on all 68, every present date is `YYYY-MM-DD`, the largest title is 96 characters, the largest url 99 and the largest snippet 3942 (about 4 KB at the default budget; `max_tokens_per_page` 64 gave about 300 characters, `search_fast_max_tokens_per_page`). A twenty-result response of about 23 KB is probe only (no fixture holds 20 results). Only the configured key is replaced (`redaction.scrub_secrets`), because search results are web pages and a page about Perplexity quotes `pplx-embed-v1-0.6b` or a `pplx-` example (lesson `redaction-patterns-need-identifier-regressions`: a regression runs a documented model id and a key-shaped example through the digest and expects both back). That scrub applies to title, snippet, url, `date` AND `last_updated`: `last_updated` is third-party text returned to the caller and is treated exactly like `date`. Caps after the scrub: title 500, url 2048, snippet 20000, `date` and `last_updated` 64 (the Agent's `DATE_CAP`, reused so the two tools agree; 32 was this change's first guess and has no evidence behind it), request id 128; they bind only on abuse. `max_tokens` drops whole results to fit (`search_fast_max_tokens_one`: three requested, one returned), so when `max_tokens` was given a warning fires if the number of items the API returned is below the asked-for number: `max_results` when given, else 10, the API default. With `max_results` omitted the shortfall is ambiguous (a rare query has fewer than ten hits), so that warning is worded as a possibility and says so (spec "Budget warning"); without `max_tokens` there is no such warning. An empty result list is a normal success with a warning (billed, D5). Titles, snippets and urls are untrusted web text: the description says so and the tool does nothing to them beyond the key replacement and caps; in particular it does not strip markup, because the caller decides how to read it. The server-runtime requirement "Secrets are never emitted" is MODIFIED (a delta under `specs/server-runtime/`) so its content carve-out names search results; its behaviour for the existing tools is unchanged.

**D5. Cost is computed, always, and one unit per request.** The response has `id` and `results` and, in all 20 committed 200 responses, nothing else: no `usage`, no cost, no `server_time` (documented, never present). So the cost is `search_usage(search_type)`, ONE helper in `search.py`: it maps the tool's `fast` to the price table's `"fast"` and `web` to `"standard"`, and returns `computed_usage(pricing.search_cost_nano(1, tier), raw=<the response's usage object when it is a dict, else None>)` (source `computed`, stamped with the price table date). The interpreter handed to `costed_call` calls it, and the tool's `cost_usd` and `cost_source` are read from the SAME `Usage` that `costed_call` returns in `Costed.recording`, so the output and the stored event cannot disagree and the web-to-standard mapping exists once. The brief said "computed unless the response reports a cost"; there is no recorded shape for a reported cost, so the rule is implemented without the exception. Relation to the main `usage-recording` "Cost source" ("Reported wins", the complete usage object kept as received): no parser is registered for `search` in `usage._PARSERS`, so a `usage` field is not a recognised cost report. It is retained (passed as `raw`, which the recorder sanitizes and stores) and the computed cost stands; a parser is added only after a probe shows a real one, and then "Reported wins" applies by the existing rule, not by anything here. Billing facts (documentation, not observable from this server): "each successful `POST /search` request" is one unit; a five-query request is one billing unit; an empty result list is therefore billed; a 4xx or 429 is not. The tool follows them: `ok` with results or without is a costed event, an error category is a cost-0 `none` event. Consequence for reviewers: `perplexity_usage` for search is the documented price times the number of successful requests, which is a lower bound only in the sense that a 200 the tool could not read (recorded `unexpected_response`, cost unknown) may have been billed.

**D6. Where the third recorder call site lives: a shared helper, `costed.costed_call`.** `agent.run_costed` is the sequence of `CLAUDE.md` "How to record usage" steps 1 to 4 (validate the project name, commit the project, timed call with no write unit, record) plus Agent-specific rules (`agent_response_status`, background submit handling, the model rule, raising on a non-finished sync status). A Search tool needs the same four steps with different interpretation. Copying it would be the third hand-written copy of the order the lessons call "the single most failure-prone rule in the codebase". Adding `if api == "search"` to `run_costed` would widen it. So the generic part moves out:

```
costed_call(app, *, tool, api, project, preset, call, record, resolve_project=True) -> Costed[T]
  # validate name, commit the project, timed call(), on PerplexityError record
  # status=exc.category (no usage) and re-raise, else record(result) -> Recording | None
  # and, when it is not None, record_usage(...); returns Costed
```

`Recording` is `(status, usage, model, preset, request_id)` where `usage` is `Usage | Mapping | None`, exactly the recorder's own parameter type (`usage.record_usage`): `agent.run_costed` passes the RAW usage mapping from the response (the recorder parses it, as today and as the unchanged `tests/test_agent_costed.py` asserts: `kwargs["usage"] == fixture(...)["usage"]`), `search.run_search` passes a parsed `Usage` from `search_usage`. `Costed` is `(result, latency_ms, project, status, recording)`: it carries the interpreted `Recording` back, which is how the Search tool reads its cost from the one `Usage` that was recorded (D5). `agent.run_costed` becomes a wrapper: it passes `call=lambda: client.create_run(...)` and an interpreter holding exactly the logic it has today (status rule, background terminal rule, model rule), then raises the unexpected-status error after `costed_call` returns, as now. `search.run_search` passes `call=lambda: client.search(body)` and an interpreter returning `Recording("ok", search_usage(search_type, raw), None, None, response.id)`. The two `record_usage(` lines (failure, response) therefore live once, in `costed_call`; `observe_job_locked` keeps its own (a background run is recorded long after the call, under a lock, which is a different shape).

**The interpreter must never raise.** It runs after the upstream call returned, when the spend has already happened; an exception out of it would lose the event and surface a bug as a failed call. Both interpreters are written total (type checks, no indexing, no parsing that can throw), and `costed_call` defends anyway: an exception from `record(...)` is logged (redacted) and the call is recorded as `unexpected_response` with no usage and no request id, then raised as `PerplexityError("unexpected_response")`. A test injects a raising interpreter and expects exactly that one event and that category (group 1).

**Test-edit consequences of the move** (a mechanical sweep, `rg -n "record_usage" tests/`): the recorder is imported into `costed.py` by name, so a test that monkeypatches `agent_module.record_usage` to watch the call made by `run_costed` no longer sees it. Exactly one does: `tests/test_agent_costed.py::test_the_recorder_runs_with_no_write_unit_open` (lines about 325 and 337, `monkeypatch.setattr(agent_module, "record_usage", probing)`); it is repointed to `costed_module.record_usage` in the same commit and its other assertions stay as they are. `agent.py` keeps its own `record_usage` import for `observe_job_locked`. The audit test changes from `{("agent.py","run_costed"): 2, ("agent.py","observe_job_locked"): 1}` to `{("costed.py","costed_call"): 2, ("agent.py","observe_job_locked"): 1}`, still "exactly two functions", and gains a sweep that `costed_call(` is called only from `run_costed` and `run_search`; its docstring says why the sites moved. The commit that does the extraction therefore touches `costed.py`, `agent.py`, `tests/test_agent_costed.py` and `tests/test_contract_checks.py`, nothing else.

**Name collision.** `tests/usage_support.py::costed_call` (an async test helper that hand-writes the sequence; `CLAUDE.md` calls it "a pure example of the whole pattern") shares its name with the production helper. It is left as is (renaming it touches every usage test) and the documentation group repoints the `CLAUDE.md` sentence: the production implementation is `costed.costed_call`, and `usage_support.costed_call` is a test-only copy of the order. *Alternative:* a second pair of `record_usage(` lines in `search.py` (a third site). Rejected for the reason above; it is the fallback if review finds the extraction too risky, at the price of three call sites and a second order to keep right. *Risk:* the refactor touches the most tested function in the repository; every existing `test_agent_costed.py` (apart from the one repointed line), `test_recording_order.py` and tool test must pass, and the mutation checks of the order are re-run against the helper (group 4).

**D7. Client.** `PerplexityClient.search(body)` is `POST /search` through `request_json` (no `timeout` override: a search took 0.14 to 0.34 s across the 20 committed 200 responses), parsed with the existing `_parse` into `SearchResponse`. The retry rules need no change: it is a POST, so it is never replayed after a response other than 429 nor after a sent-request timeout, and is replayed after a connect failure and a 429 (the 429 honors `Retry-After`). Nothing in the Search API puts an id in a path, so no id check is needed. `models/search.py` holds one model, `SearchResponse`: `results: list[Any]` (required), `id: Any = None`, `extra="allow"`. Items are NOT typed: the Agent models set the precedent (`output: Any`) because a billed 200 must never be lost to a schema quibble, and a typed item (`title: str`) would turn a JSON null title, a numeric date or a non-object item into an `unexpected_response` for a request that was charged. `results` not being a list is the one shape failure kept as `unexpected_response` (nothing can be read from it), as is a body without `results`. The output item model (`SearchResult`, with typed `str` and `str | None` fields) lives in `search.py` and is built by the digest (D4). The OpenAPI file also requires `id`; the tool records the event with a null request id if it is absent or not a string. The request id is the body `id`: it equals the `x-request-id` header in all 20 committed 200 responses, and the client does not expose headers to its callers, so there is no header fallback to build. The 401 response has no `x-request-id` header; the 15 committed 400 responses have one.

**D8. Errors.** The Search API does not use the documented 422 validation envelope: every validation failure is 400 `{"error": {"message", "type", "code"}}` with `type` `invalid_request`, `invalid_country_code`, `invalid_language_code` or (401) `invalid_api_key`; `search_invalid_body_400` (truncated JSON) is `invalid request body`. The existing mapping by status (400 and 422 to `invalid_request`, 401 to `authentication`, 429 to `rate_limited`) handles all of it and the API's message passes through redacted with `api_message` set, so no client change is needed beyond the call. Where the probe showed a clear API message we still validate locally: a local refusal makes no call, records no failure event and costs no rate-limit unit. The 429 body of the Search API was not captured; the generic status mapping and the `Retry-After` rule apply, covered by an inline response.

**D9. Output shape.** `SearchResult` items (`title`, `url`, `snippet`, `date`, `last_updated`); `SearchOutput`: `results`, `count`, `query_count`, `search_type`, `request_id`, `cost_usd` (exact string from `format_usd`), `cost_source`, `latency_ms`, `project`, `warnings`. Two departures from `AskResult`, on purpose: the id is `request_id` (not `response_id`) because this is a request that returns a list, the Search API names it `id` and the `x-request-id` header, and the usage event and `perplexity_usage` call the column the request id; and cost is two flat fields rather than a nested `usage` object because the API reports no tokens, so the Agent `UsageSummary` would carry three permanently null fields. Both come from the one `Usage` that `costed_call` returned (D5). Text content is a short numbered rendering (title, url, date, snippet) then one usage line. Money is always the exact string, never a float.

**D10. Context cost of one more tool.** `tools/list` was 10564 bytes with three tools and about 40.5 KB with seven (CLAUDE.md "How to add a tool", measured 2026-10-09). The new tool's input schema has about 15 parameters and its output schema nested results. The description is kept to the facts a caller needs (costs, third-party content, merge semantics, what is refused) and the growth is measured the same way (`wc -c` on one `tools/list` response, before and after) in group 3 and written into Risks. Trimming existing descriptions is the lever if the figure is unacceptable; the design target stays about nine tools.

**D11. Tests.** Offline, through `build_server` with a `MockTransport` serving the recorded fixtures (`agent_support.make_world`; the pattern of `tests/test_ask_tool.py`), a request-capturing transport for exact request bodies, and the mutation-check rule (`docs/lessons/cleanup-tests-must-fail-when-cleanup-is-removed.md`) for: the recorder-order test against the helper (record inside a write unit loses the event), the project-resolved-first test (move resolution after the call and the failed-call project test goes red), the always-send-`search_type` test (omit it and the default-is-fast test goes red), and the local mixed-domain refusal (remove it and the request goes out). Lessons applied: `redaction-patterns-need-identifier-regressions` (model id and key-shaped example in a snippet), `best-effort-writers-and-the-callers-write-lock` (recording order pinned for the search tool), `dedupe-index-only-covers-the-statuses-it-names` (search events are `ok` and keyed by a unique response id, so the index covers them; failure events have no key and always store, and the tool never re-records a response), `framework-logs-carry-bound-parameters` (a search stores no content, so only the usage event is written; the query never reaches a log: the client logs method, path and status). **Test-world hazards.** The `usage_events` table has a partial unique index (`uq_usage_events_api_request_id`) that keeps one `ok` event per `(api, request_id)` (`dedupe-index-only-covers-the-statuses-it-names`), so a second `ok` call that returns the same fixture body inside one database stores NO event and the test would read it as a recording bug. Every test that makes two or more successful search calls in one database therefore serves a different fixture (distinct `id`) to each, or an inline copy with its own `id`; all 20 committed 200 fixtures have distinct ids. And `Scripted` in `tests/test_wiring_one_event_per_call.py` routes POSTs by method only: it must dispatch on `request.url.path` (`/search` to the search fixtures in call order, `/v1/agent` as today) before a search can be added to it (group 5).

Fixture-to-scenario map: `search_fast_single` (result shape, cost 0.001, request id, headers), `search_web_single` (cost 0.005), `search_omitted_search_type_accepted` (an omitted type is sent as `fast` by the tool), `search_unknown_field_accepted` (a request the tool cannot build), `search_fast_multi_query` and `_duplicate` (merge), `search_fast_allow_domain`, `_deny_domain` and `_mixed_domains_accepted` (domain request shapes and the refusal), `search_fast_recency_month`, `_date_range_inclusive`, `_date_range_empty`, `_updated_range`, `_recency_with_updated_accepted` (date and recency shapes, empty result), `search_fast_max_tokens_one`, `_max_tokens_per_page`, `_page_tokens_above_total` (budget, dropped results), `search_fast_language_11_accepted` and `_uppercase_accepted` (the language bounds), `search_whitespace_query_empty` (the local refusal's reason), the six requests that are not reproduced (D2) and the `search_*_400` and `_401` fixtures (error mapping, failure events). The live tests (`-m live`) are the acceptance group only.

**D12. Page snippets are a non-goal.** The CLI documents `pplx content snippets "<query>" <url>...` (up to 50 urls, `--max-tokens` 1 to 16384, `--max-tokens-per-page` 1 to 4096), output `results[{url, text, tokens_count | error}]`. `openapi.json` lists 18 paths (`/search`, `/v1/agent*`, `/v1/async/sonar*`, `/v1/embeddings`, `/v1/contextualizedembeddings`, `/v1/models`, `/v1/skills*`, `/v1/sonar`, analytics) and none of them is a content or snippets endpoint, and neither the CLI page nor the Search quickstart names an HTTP route for it. Calling an endpoint by guessing its path would be probing an undocumented API with a billed key, so the capability is out of scope; the CLI's documented token ranges are reused as the bounds of `max_tokens` (D2) because they describe the same budget.

## Risks / Trade-offs

- **Cost is computed, never reported** (D5) -> `cost_source` says `computed`; `perplexity_usage` shows documented price times successful requests. Billing of empty results and of a whitespace query is documented, not observed; the acceptance reconciles the server's own books to the nano-USD and cannot prove the provider's invoice. A manual look at the Perplexity console after acceptance is the only external check.
- **Multi-query results cannot be attributed** (D3) -> warning and description; a caller who needs attribution makes one call per query (a fast call is $0.001).
- **Snippet volume** (D4): twenty default-budget results are about 23 KB of text in the caller's context (probe only: no fixture holds 20 results; the committed ceiling is 3942 characters for one snippet), twice when a client reads both the text and structured content -> `max_tokens_per_page` and `max_tokens` exist; the description names them; the default `max_results` is the API's 10, not lowered, because a lower default is a product choice nobody measured (reviewers: a default of 5 is the alternative).
- **Third-party content is untrusted** (D4): a snippet can carry instructions aimed at the reading model -> the description says it is third-party web content; nothing in the tool executes or follows it. A caller that pipes snippets into another model owns that boundary.
- **`recency` with `last_updated_*` is refused though the API accepts it** (D2) -> conservative on the documented rule; one scenario to relax if a probe shows the combination applies both filters.
- **`max_tokens` and `max_tokens_per_page` caps are our own** (D2) -> labelled as such in the spec; raising them is a constant.
- **The shared-helper refactor touches `run_costed`** (D6) -> every existing test passes with one repointed monkeypatch (`tests/test_agent_costed.py`), the order mutation-checked against the helper, a documented fallback.
- **`costed_call`'s name is also a test helper's** (D6) -> `tests/usage_support.py::costed_call` stays; the `CLAUDE.md` pointer is updated to say it is a test-only copy.
- **Search text enters `server-runtime`'s carve-out** (D4) -> a MODIFIED delta of "Secrets are never emitted"; the key is still replaced everywhere, only the list of content that may hold key-shaped examples grows.
- **429 of the Search API is unobserved** (D8) -> generic status mapping and `Retry-After`; the provider limit seen is 50 request units per one-second window, probably counted per query for a multi-query request (`search_fast_multi_query` reads 3, see D3), so a five-query request can trip it alone only in a burst; invalid requests do not count (120 parallel 400s drew no 429).
- **A readable-200 failure may have been billed** (D5) -> recorded `unexpected_response`, cost unknown, counted by `calls_cost_unknown`.
- **The tool surface grows from 7 to 8** (D10) -> measured in group 3.
- **`date` and `last_updated` semantics are the API's** -> returned as given; the tool does not parse or normalize them (all 114 present `date` and `last_updated` values in the 20 committed 200 responses are `YYYY-MM-DD`).

## Observed shapes (the evidence for the decisions above)

Captured 2026-10-09 (`tests/fixtures/search_*.json`; sidecars carry the request, the latency, the `x-request-id` and `x-ratelimit-*` headers). What the documentation says against what the API did:

| Documentation | Observed |
|---|---|
| Errors: 422 `HTTPValidationError` (OpenAPI) | every failure is 400 `{"error": {"message", "type", "code"}}`; types `invalid_request`, `invalid_country_code`, `invalid_language_code`, `invalid_api_key` (401); a truncated JSON body is 400 `invalid request body` |
| `max_results` maximum 50 (schema) | 21 and 0 are refused for `fast` (`search_max_results_21_400`): `max results must be between 1 and 20`; for `web` alike is probe only |
| Language codes: up to 10 (prose), 20 (schema), lowercase only | 11 accepted, 21 refused (`cannot have more than 20 languages`); `EN` accepted; `xx` refused (`invalid_language_code`, `search_bad_language_400`); `eng` probe only |
| Allowlist or denylist, "not both" | a mixed list is accepted and equals the allowlist-only result: deny entries are ignored |
| Recency cannot combine with any date filter | refused with a clear message for publication dates; accepted with `last_updated_*` |
| Dates must be `MM/DD/YYYY` | `2026-03-01` refused with `must be in MM/DD/YYYY format` (`search_bad_date_iso_400`); both bounds inclusive (`search_fast_date_range_inclusive`); `9/1/2026` accepted, `yesterday` and `13/45/2026` refused: probe only |
| Multi-query: "each query is processed independently" | one flat merged list, `max_results` a total, no query tag; billing 1 unit (documented), rate limit probably +1 per query (`x-ratelimit-used` 3 in `search_fast_multi_query`) |
| `max_tokens`: "maximum total content tokens" | a small value drops whole results (1 gave one result of three requested) |
| Response has `results`, `id`, `server_time` | `server_time` never present (20 committed 200 responses; 32 in the probe); no `usage` or cost field; `id` equals the `x-request-id` header in 20 of 20; `date` absent (not null) on 22 of 68 results (32%), `last_updated` present on 68 of 68 |
| Unknown request fields: not discussed | accepted with a 200 (`search_unknown_field_accepted`; billed on the documented rule) |
| Empty or whitespace query | empty string and `[]` and a blank list element are 400 (`query 1 length must be between 1 and 8192`); `"   "` is a 200 with `results: []` (`search_whitespace_query_empty`); the blank list element is probe only |
| Page snippets: CLI-only (`pplx content snippets`) | no HTTP route in `openapi.json` or any fetched page |

Latency in the committed 200 sidecars: 0.14 to 0.34 s (18 fast; one web call, 0.30 s: too few to claim a difference); the probe's 0.14 to 0.52 s over 32 calls is probe only. Headers on 200: `x-request-id`, `x-ratelimit-limit` 50, `-remaining`, `-used`, `-reset` (the response time plus one second: a one-second window), a Cloudflare `server` header and `set-cookie` values (not recorded in the fixtures). On 400: `x-request-id` only. On 401: neither. Invalid requests did not draw a 429 in a burst of 120 parallel ones (probe only, no fixture).
