# Design

## Context

See `proposal.md` for motivation and `specs/` for requirements. State that shapes the approach:

- Foundation, usage-log and agent-api are archived (2026-10-09). The server has a client (`client.py`: `request_json` with the create-POST retry rules, `_parse`, redacted `PerplexityError` with `api_message`), the closed eleven-value error vocabulary, a unit of work, project resolution and a recorder (`usage.py: record_usage`, `computed_usage`, `format_usd`) whose caller contract is `CLAUDE.md` "How to record usage". `pricing.search_cost_nano(requests, search_type)` already exists and is pinned to the documented price table (`"standard"` $5/1k, `"fast"` $1/1k). No Search parser is registered in `usage._PARSERS`, and none is needed: the response carries no usage.
- The recorder's production call sites today are `agent.run_costed` (two `record_usage(` lines) and `agent.observe_job_locked` (one), pinned by `tests/test_contract_checks.py::test_record_usage_is_called_from_exactly_two_functions_and_defined_once`.
- The Search API was probed live on 2026-10-09 (spend about $0.044 over 32 billed requests, plus 120 free parallel invalid requests). The captures are committed as `tests/fixtures/search_*.json` with sidecars (`63dcb0f`). Every spec scenario that names "the recorded ..." uses one of them through `httpx2.MockTransport`. Lesson `docs-lie-probe-the-api-first`: the documentation was wrong or silent on eleven points (see "Observed shapes").
- Tool modules must not use `from __future__ import annotations`; every tool is `register(server)`, typed with `Annotated[..., Field(description=...)]`, returns `ToolResult(content=..., structured_content=...)` and raises `PerplexityError` for anticipated failures.
- The live server runs under pm2 on port 8102 and must not be touched by development or tests; the live acceptance (group 6) is the one place a human restarts it.

## Goals / Non-Goals

**Goals:**
- One cheap-by-default tool that returns ranked web results as structured data, with every filter the API offers for the two cheap search types.
- Every request recorded exactly once through the existing recorder, in the contract's order, without a third hand-written copy of the sequence.
- Local validation of every input the probe showed the API accepts wrongly, bills for nothing, or reports misleadingly.
- Honest output: no attribution the API does not give, no cost the API did not report presented as reported.

**Non-Goals:**
- `people` search (price undocumented, returns individuals' professional data), page snippets (D12), contextualized content extraction, search as an Agent tool, result caching, streaming, pagination beyond `max_results`, a cost ceiling or per-minute throttle, surfacing the rate-limit headers.
- A Search usage parser (D5): nothing to parse until the API reports usage.

## Decisions

**D1. One tool, three new modules and one shared helper.** The name is fixed by the product intent: `perplexity_search`. Layout: `models/search.py` (`SearchResult`, `SearchResponse`), `search.py` (option validation, request building, digestion, `run_search`), `costed.py` (the shared costed-call sequence, D6), `tools/search.py`. Annotations: `readOnlyHint` false (it writes a usage event and may create a project), `destructiveHint` false, `openWorldHint` true, like `perplexity_ask`. One tool with a `query` that is a string or a list, not a `perplexity_multi_search`: the two differ in one argument and one billing fact, and a second schema would cost every session's context twice (D10). *Alternative:* extend `perplexity_ask` with a no-LLM mode. Rejected: different output shape, different cost model, different failure modes.

**D2. Request building is one pure function** (`search.build_request(options)`), tested against the recorded request shapes (each sidecar carries its `request`). Rules and the probe evidence behind each:

| Rule | Evidence |
|---|---|
| Filters are TOP-LEVEL fields (`search_domain_filter`, `search_recency_filter`, `search_after_date_filter`, `search_before_date_filter`, `last_updated_after_filter`, `last_updated_before_filter`, `search_language_filter`, `country`, `max_results`, `max_tokens`, `max_tokens_per_page`), unlike the Agent API where they sit inside a tool's `filters` | every `search_*` sidecar; OpenAPI `ApiSearchRequest` |
| `search_type` is ALWAYS sent (`fast` by default) | an omitted `search_type` ran a standard ($0.005) search (`search_fast_*` vs the probe `f_nosearchtype`); only an explicit `fast` is the cheap one |
| `search_type` is `fast` or `web`; `people` refused | API enum is web, fast, people (`search_bad_search_type_400`); `people` price is undocumented and the result type is personal data |
| `query` is a string or 1 to 5 strings, each non-blank, at most 8192 characters | `search_too_many_queries_400` (`maximum 5 queries allowed, got 6`), `search_empty_query_400` (`query 1 length must be between 1 and 8192 characters, got 0`), `search_missing_query_400` (empty list: `query is required`); a whitespace-only query was a 200 with `results: []` (`search_whitespace_query_empty`), which the docs bill, so it is refused locally |
| `max_results` 1 to 20 | `search_max_results_21_400` and `_0_400` (`max results must be between 1 and 20`), for fast and web alike; the OpenAPI schema says maximum 50 (people only) |
| Dates: `YYYY-MM-DD` in, `MM/DD/YYYY` out, strict, order checked | `search_bad_date_iso_400` (the API refuses ISO, unlike the Agent API, which accepted it); `9/1/2026` (no padding) was accepted; `13/45/2026` refused with the same message; both bounds are inclusive (`search_fast_date_range_inclusive`: results dated 2026-09-01 and 2026-10-01 came back for 09/01 to 10/01) |
| Recency alone, never with any date option | `search_recency_with_dates_400` (clear API message for publication dates); but recency with `last_updated_after_filter` was ACCEPTED (`search_fast_recency_with_updated_accepted`) although the docs say recency cannot combine with any date filter. The effect of that combination is unobserved (whether both filters applied cannot be told from ten results), so it is refused locally on the documented rule. Relaxing it is one scenario and one branch |
| Domains: at most 20, each at most 253 characters, no empty or `-` or whitespace entry, no mixing | `search_domains_21_400` (`search domain filter must be at most 20`), OpenAPI `maxLength` 253; a mixed list was ACCEPTED and the response equals the allowlist-only response (`search_fast_mixed_domains_accepted` against `search_fast_allow_domain`), so the deny entry is silently ignored: that is not a result the caller asked for |
| Languages: at most 20, each two lowercase ASCII letters | `search_language_21_400` (`cannot have more than 20 languages`); 11 codes accepted (`search_fast_language_11_accepted`) although the prose says 10; `["EN"]` accepted (`search_fast_language_uppercase_accepted`) although the docs say lowercase only; `xx` and `eng` refused by the API as `invalid_language_code` (`search_bad_language_400`), which stays the API's job: this server holds no ISO list |
| Country: two ASCII letters, sent upper case | `ZZ` and `USA` refused by the API as `invalid_country_code` (`search_bad_country_400`); `us` accepted. Validity of the code stays the API's job |
| `max_tokens` 1 to 16384 and `max_tokens_per_page` 1 to 4096 | the API accepts 1 to 1000000 (`search_max_tokens_0_400`). The tighter bounds are this server's own caps, borrowed from the documented ranges of the CLI's `content snippets` command (16384 and 4096), so one call cannot pull a million tokens of web text into the caller's context; labelled as such in the spec. A per-page budget above the total was accepted (`search_fast_page_tokens_above_total`) so no cross-check is made |
| Nothing else is sent | an unknown field (`bogus_param`) was accepted and billed (probe `e_unknown`), so a typo would otherwise be silent |

**How the request tests compare.** Each recorded request is rebuilt from the options that produce it and compared with the sidecar's `request` exactly (the tool's option names differ from the API's field names, so the test carries a small table from sidecar field to option). Shapes with no sidecar (the minimal request, a combination) are asserted from inline expected dicts written in the test and labelled as having no recording behind them.

**D3. Several queries come back merged, and the tool says so.** A request with three queries returned ONE flat `results` list (`search_fast_multi_query`: ten results for `max_results` 10, from `rust borrow checker`, `golang generics` and `zig comptime`), with no field naming the query, no grouping and no per-query rank; `max_results` is a total across the queries, not per query. The same query sent twice returned one list of four distinct urls (`search_fast_multi_query_duplicate`): the API de-duplicates urls, the tool does not touch the list. The documentation says each query is "processed independently", which is true of the work and not of the output. The tool therefore cannot attribute results to queries, and does not pretend to: it returns the API's list unchanged, sets `query_count`, adds one warning, and the description says that a caller who needs per-query results makes one call per query. Billing: one unit per request, rate limit: one unit per query (`x-ratelimit-used` rose by 3 for the three-query request and by 2 for the repeated-query one, limit 50 per one-second window), so a five-query request is five times closer to a 429 than a single query but costs the same as one.

**D4. Result digestion is one function** (`search.digest(response, secrets)`). `results[]` map to `{title, url, snippet, date, last_updated}` in the API's order. The snippet is the API's page excerpt; it can run to about 4 KB at the default budget (largest of 137 captured results: 3942 characters; twenty results about 23 KB, `search_fast_*` with `max_results` 20) and shrinks with `max_tokens_per_page` (64 gave about 300 characters). Dates are `YYYY-MM-DD` in all 137 captured results; `date` was absent (not null) on 44 of them and `last_updated` was always present; absent becomes `None`. Third-party content is treated like an answer in `agent-ask`: only the configured key is replaced (`redaction.scrub_secrets`), because search results are web pages and a page about Perplexity quotes `pplx-embed-v1-0.6b` or a `pplx-` example (the lesson `redaction-patterns-need-identifier-regressions` applies: a regression test runs a documented model id and a key-shaped example through the digest and expects both back). Caps (title 500, url 2048, snippet 20000, date 32, request id 128) bound a result's size; the largest captured title was 120 characters and url 160, so they bind only on abuse or a future change. `max_tokens` drops whole results to fit (`search_fast_max_tokens_one`: three requested, one returned), so a warning fires when `max_tokens` was given and the count is below the effective `max_results` (the given value, else 10). An empty result list is a normal success with a warning (billed, D5). A result without a url is dropped with a warning (a pointer to nowhere is not a result); the tolerant model keeps it, the digest decides. Titles, snippets and urls are untrusted web text: the description says so and the tool does nothing to them beyond the key replacement and caps, in particular it does not strip markup, because the caller decides how to read it.

**D5. Cost is computed, always, and one unit per request.** The response has `id` and `results` and, in all 32 captured 200 responses, nothing else: no `usage`, no cost, no `server_time` (documented, never present). So the cost is `pricing.search_cost_nano(1, "fast" | "standard")` wrapped by `computed_usage` (source `computed`, stamped with the price table date). The brief said "computed unless the response reports a cost"; there is no recorded shape for a reported cost, so the rule is implemented without the exception, and a scenario pins that a `usage` field, if one ever appears, is retained by the tolerant model and ignored (a Search parser is registered in `usage._PARSERS` only after probing a real one, the CLAUDE.md rule). Billing facts (documentation, not observable from this server): "each successful `POST /search` request" is one unit; a five-query request is one billing unit; an empty result list is therefore billed; a 4xx or 429 is not. The tool follows them: `ok` with results or without is a costed event, an error category is a cost-0 `none` event. Consequence for reviewers: `perplexity_usage` for search is the documented price times the number of successful requests, which is a lower bound only in the sense that a 200 the tool could not read (recorded `unexpected_response`, cost unknown) may have been billed.

**D6. Where the third recorder call site lives: a shared helper, `costed.costed_call`.** `agent.run_costed` is the sequence of `CLAUDE.md` "How to record usage" steps 1 to 4 (validate the project name, commit the project, timed call with no write unit, record) plus Agent-specific rules (`agent_response_status`, background submit handling, the model rule, raising on a non-finished sync status). A Search tool needs the same four steps with different interpretation. Copying it would be the third hand-written copy of the order the lessons call "the single most failure-prone rule in the codebase". Adding `if api == "search"` to `run_costed` would widen it. So the generic part moves out:

```
costed_call(app, *, tool, api, project, preset, call, record, resolve_project=True) -> Costed[T]
  # validate name, commit the project, timed call(), on PerplexityError record
  # status=exc.category (no usage) and re-raise, else record(result) -> Recording | None
  # and, when it is not None, record_usage(...); returns the result, latency, project, status
```

`Recording` is `(status, usage, model, preset, request_id)`. `agent.run_costed` becomes a wrapper: it passes `call=lambda: client.create_run(...)` and an interpreter holding exactly the logic it has today (status rule, background terminal rule, model rule), then raises the unexpected-status error after `costed_call` returns, as now. `search.run_search` passes `call=lambda: client.search(body)` and an interpreter returning `Recording("ok", computed_usage(...), None, None, response.id)`. The two `record_usage(` lines (failure, response) therefore live once, in `costed_call`; `observe_job_locked` keeps its own (a background run is recorded long after the call, under a lock, which is a different shape). The audit test changes from `{("agent.py","run_costed"): 2, ("agent.py","observe_job_locked"): 1}` to `{("costed.py","costed_call"): 2, ("agent.py","observe_job_locked"): 1}`, still "exactly two functions", and gains a sweep that `costed_call(` is called only from `run_costed` and `run_search`; its docstring says why the sites moved. Search writes nothing of its own after the call, so step 5 of the contract is empty. *Alternative:* a second pair of `record_usage(` lines in `search.py` (a third site). Rejected for the reason above; it is the fallback if review finds the extraction too risky, at the price of three call sites and a second order to keep right. *Risk:* the refactor touches the most tested function in the repository; every existing `test_agent_costed.py`, `test_recording_order.py` and tool test must pass unchanged, and the mutation checks of the order are re-run against the helper (group 4).

**D7. Client.** `PerplexityClient.search(body)` is `POST /search` through `request_json` (no `timeout` override: a search took 0.14 to 0.52 s in 32 calls), parsed with the existing `_parse` into `SearchResponse`. The retry rules need no change: it is a POST, so it is never replayed after a response other than 429 nor after a sent-request timeout, and is replayed after a connect failure and a 429 (the 429 honors `Retry-After`). Nothing in the Search API puts an id in a path, so no id check is needed. `models/search.py`: `SearchResult` (`title`, `url`, `snippet` default `""`; `date`, `last_updated` default `None`; `extra="allow"`) and `SearchResponse` (`results: list[SearchResult]` required, `id: str | None = None`, `extra="allow"`). Only `results` is required so that a billed 200 is never lost to a schema quibble (the Agent models do the same); the OpenAPI file also requires `id`, and the tool records the event with a null request id if it is ever absent. The request id is the body `id`: it equals the `x-request-id` header in all 32 captured 200 responses, and the client does not expose headers to its callers, so there is no header fallback to build. The 401 response has no `x-request-id` header; 400 responses have one.

**D8. Errors.** The Search API does not use the documented 422 validation envelope: every validation failure is 400 `{"error": {"message", "type", "code"}}` with `type` `invalid_request`, `invalid_country_code`, `invalid_language_code` or (401) `invalid_api_key`; `search_invalid_body_400` (truncated JSON) is `invalid request body`. The existing mapping by status (400 and 422 to `invalid_request`, 401 to `authentication`, 429 to `rate_limited`) handles all of it and the API's message passes through redacted with `api_message` set, so no client change is needed beyond the call. Where the probe showed a clear API message we still validate locally: a local refusal makes no call, records no failure event and costs no rate-limit unit. The 429 body of the Search API was not captured; the generic status mapping and the `Retry-After` rule apply, covered by an inline response.

**D9. Output shape.** `SearchResult` items (`title`, `url`, `snippet`, `date`, `last_updated`); `SearchOutput`: `results`, `count`, `query_count`, `search_type`, `request_id`, `cost_usd` (exact string from `format_usd`), `cost_source`, `latency_ms`, `project`, `warnings`. There is no `usage` object and no token counts (the API reports none), so the output does not reuse the Agent `UsageSummary` (it would carry three permanently null fields). Text content is a short numbered rendering (title, url, date, snippet) then one usage line. Money is always the exact string, never a float.

**D10. Context cost of one more tool.** `tools/list` was 10564 bytes with three tools and about 40.5 KB with seven (CLAUDE.md "How to add a tool", measured 2026-10-09). The new tool's input schema has about 15 parameters and its output schema nested results. The description is kept to the facts a caller needs (costs, third-party content, merge semantics, what is refused) and the growth is measured the same way (`wc -c` on one `tools/list` response, before and after) in group 3 and written into Risks. Trimming existing descriptions is the lever if the figure is unacceptable; the design target stays about nine tools.

**D11. Tests.** Offline, through `build_server` with a `MockTransport` serving the recorded fixtures (`agent_support.make_world`; the pattern of `tests/test_ask_tool.py`), a request-capturing transport for exact request bodies, and the mutation-check rule (`docs/lessons/cleanup-tests-must-fail-when-cleanup-is-removed.md`) for: the recorder-order test against the helper (record inside a write unit loses the event), the project-resolved-first test (move resolution after the call and the failed-call project test goes red), the always-send-`search_type` test (omit it and the default-is-fast test goes red), and the local mixed-domain refusal (remove it and the request goes out). Lessons applied: `redaction-patterns-need-identifier-regressions` (model id and key-shaped example in a snippet), `best-effort-writers-and-the-callers-write-lock` (recording order pinned for the search tool), `dedupe-index-only-covers-the-statuses-it-names` (search events are `ok` and keyed by a unique response id, so the index covers them; failure events have no key and always store, and the tool never re-records a response), `framework-logs-carry-bound-parameters` (a search stores no content, so only the usage event is written; the query never reaches a log: the client logs method, path and status). Fixture-to-scenario map: `search_fast_single` (result shape, cost 0.001, request id, headers), `search_web_single` (cost 0.005), `search_fast_multi_query` and `_duplicate` (merge), `search_fast_allow_domain`, `_deny_domain` and `_mixed_domains_accepted` (domain request shapes and the refusal), `search_fast_recency_month`, `_date_range_inclusive`, `_date_range_empty`, `_updated_range`, `_recency_with_updated_accepted` (date and recency shapes, empty result), `search_fast_max_tokens_one`, `_max_tokens_per_page`, `_page_tokens_above_total` (budget, dropped results), `search_fast_language_11_accepted` and `_uppercase_accepted` (the language bounds), `search_whitespace_query_empty` (the local refusal's reason), and the `search_*_400` and `_401` fixtures (error mapping, failure events). The live tests (`-m live`) are the acceptance group only.

**D12. Page snippets are a non-goal.** The CLI documents `pplx content snippets "<query>" <url>...` (up to 50 urls, `--max-tokens` 1 to 16384, `--max-tokens-per-page` 1 to 4096), output `results[{url, text, tokens_count | error}]`. `openapi.json` lists 18 paths (`/search`, `/v1/agent*`, `/v1/async/sonar*`, `/v1/embeddings`, `/v1/contextualizedembeddings`, `/v1/models`, `/v1/skills*`, `/v1/sonar`, analytics) and none of them is a content or snippets endpoint, and neither the CLI page nor the Search quickstart names an HTTP route for it. Calling an endpoint by guessing its path would be probing an undocumented API with a billed key, so the capability is out of scope; the CLI's documented token ranges are reused as the bounds of `max_tokens` (D2) because they describe the same budget.

## Risks / Trade-offs

- **Cost is computed, never reported** (D5) -> `cost_source` says `computed`; `perplexity_usage` shows documented price times successful requests. Billing of empty results and of a whitespace query is documented, not observed; the acceptance reconciles the server's own books to the nano-USD and cannot prove the provider's invoice. A manual look at the Perplexity console after acceptance is the only external check.
- **Multi-query results cannot be attributed** (D3) -> warning and description; a caller who needs attribution makes one call per query (a fast call is $0.001).
- **Snippet volume** (D4): twenty default-budget results are about 23 KB of text in the caller's context, twice when a client reads both the text and structured content -> `max_tokens_per_page` and `max_tokens` exist; the description names them; the default `max_results` is the API's 10, not lowered, because a lower default is a product choice nobody measured (reviewers: a default of 5 is the alternative).
- **Third-party content is untrusted** (D4): a snippet can carry instructions aimed at the reading model -> the description says it is third-party web content; nothing in the tool executes or follows it. A caller that pipes snippets into another model owns that boundary.
- **`recency` with `last_updated_*` is refused though the API accepts it** (D2) -> conservative on the documented rule; one scenario to relax if a probe shows the combination applies both filters.
- **`max_tokens` and `max_tokens_per_page` caps are our own** (D2) -> labelled as such in the spec; raising them is a constant.
- **The shared-helper refactor touches `run_costed`** (D6) -> every existing test unchanged, the order mutation-checked against the helper, a documented fallback.
- **429 of the Search API is unobserved** (D8) -> generic status mapping and `Retry-After`; the provider limit seen is 50 request units per one-second window, counted per query for a multi-query request, so a five-query request can trip it alone only in a burst; invalid requests do not count (120 parallel 400s drew no 429).
- **A readable-200 failure may have been billed** (D5) -> recorded `unexpected_response`, cost unknown, counted by `calls_cost_unknown`.
- **The tool surface grows from 7 to 8** (D10) -> measured in group 3.
- **`date` and `last_updated` semantics are the API's** -> returned as given; the tool does not parse or normalize them (all 137 captured values were `YYYY-MM-DD`).

## Migration Plan

1. Land the client models and `search()` with fixture tests; no tool yet.
2. Land request building and validation, then digestion and the tool (registered last, so `tests/test_server.py` changes once).
3. Extract `costed.costed_call` with every existing test green and unchanged, then wire `run_search` to it and update the audit test in the same commit.
4. Acceptance group: restart pm2 (human), reconnect the `perplexity` MCP server, call the tool at the cheapest settings, read `perplexity_usage`. No migration, so no backup is taken and the database is untouched.
5. Rollback: revert the merge; nothing persists besides usage events, which stay valid history.

## Open Questions

- Whether a later epic wants `perplexity_ask` to expose a search-only mode or the routing epic to choose between `ask` and `search` (does not change this change's shape).
- Whether to surface the `x-ratelimit-*` headers (the client does not expose headers today; answerable after real use shows 429s).

## Observed shapes (the evidence for the decisions above)

Captured 2026-10-09 (`tests/fixtures/search_*.json`; sidecars carry the request, the latency, the `x-request-id` and `x-ratelimit-*` headers). What the documentation says against what the API did:

| Documentation | Observed |
|---|---|
| Errors: 422 `HTTPValidationError` (OpenAPI) | every failure is 400 `{"error": {"message", "type", "code"}}`; types `invalid_request`, `invalid_country_code`, `invalid_language_code`, `invalid_api_key` (401); a truncated JSON body is 400 `invalid request body` |
| `max_results` maximum 50 (schema) | 21 is refused for `fast` and `web` alike: `max results must be between 1 and 20` |
| Language codes: up to 10 (prose), 20 (schema), lowercase only | 11 accepted, 21 refused (`cannot have more than 20 languages`); `EN` accepted; `xx`, `eng` refused (`invalid_language_code`) |
| Allowlist or denylist, "not both" | a mixed list is accepted and equals the allowlist-only result: deny entries are ignored |
| Recency cannot combine with any date filter | refused with a clear message for publication dates; accepted with `last_updated_*` |
| Dates must be `MM/DD/YYYY` | `9/1/2026` accepted; `2026-03-01`, `yesterday`, `13/45/2026` refused with `must be in MM/DD/YYYY format`; both bounds inclusive |
| Multi-query: "each query is processed independently" | one flat merged list, `max_results` a total, no query tag; billing 1 unit (documented), rate limit +N units (observed) |
| `max_tokens`: "maximum total content tokens" | a small value drops whole results (1 gave one result of three requested) |
| Response has `results`, `id`, `server_time` | `server_time` never present (32 responses); no `usage` or cost field; `id` equals the `x-request-id` header in 32 of 32; `date` absent (not null) on 44 of 137 results, `last_updated` always present |
| Unknown request fields: not discussed | accepted and billed (`bogus_param`) |
| Empty or whitespace query | empty string and `[]` and a blank list element are 400 (`query 1 length must be between 1 and 8192`); `"   "` is a 200 with `results: []` |
| Page snippets: CLI-only (`pplx content snippets`) | no HTTP route in `openapi.json` or any fetched page |

Latency 0.14 to 0.52 s per call (fast 0.14 to 0.43 s, web 0.30 to 0.52 s over three web calls: too few to claim a difference). Headers on 200: `x-request-id`, `x-ratelimit-limit` 50, `-remaining`, `-used`, `-reset` (the response time plus one second: a one-second window), a Cloudflare `server` header and `set-cookie` values (not recorded in the fixtures). On 400: `x-request-id` only. On 401: neither. Invalid requests did not draw a 429 in a burst of 120 parallel ones.
