# Proposal

## Why

The server can answer a question (`perplexity_ask`) but cannot hand the caller raw, ranked web results to read for itself. Perplexity's Search API (`POST /search`) returns exactly that as structured JSON, at $0.001 per fast request and $0.005 per standard one, with no LLM in the loop. It is also the cheapest way for a coding agent to look something up, and the 2.0.0 rewrite lists it as the next tool (CLAUDE.md "Not built yet"). This change adds one tool, `perplexity_search`, and makes its spend visible: it is the third producer of usage events, and the first whose cost is never reported by the API and must be computed from the documented prices.

The Search API was probed live on 2026-10-09 (32 billed requests, about $0.044; 34 captures recorded as `tests/fixtures/search_*.json`, committed before this change in `63dcb0f`). The probe contradicted the documentation in places that shape the design: every error is HTTP 400 with a flat `{"error": {...}}` body, not the documented 422 validation envelope; `max_results` stops at 20 for both search types although the schema says 50; the language filter takes up to 20 codes (prose says 10) and accepts upper case; a mixed allow and deny domain list is accepted and the deny entries are silently ignored; a recency filter is accepted next to `last_updated_*` bounds although documented as exclusive; a multi-query request returns one flat merged list with nothing that says which query produced which result; a small `max_tokens` drops whole results; a whitespace-only query is a billed 200 with no results; unknown request fields are silently accepted; and the documented `server_time` and any cost or usage field never appear. See `design.md` "Observed shapes".

## What Changes

- Add one tool, `perplexity_search`, with typed parameters, an output model and annotations like the existing tools. Default search type is `fast` ($0.001); `web` ($0.005) is opt-in; `people` is not exposed (its price is undocumented and it returns individuals' professional data). The tool returns `results` (title, url, snippet, date, last_updated) in the order the API ranks them, a `count`, the search type, the request id, an exact decimal USD cost with its source, the latency and warnings. Titles and snippets are third-party web content and the description says so.
- Accept `query` as one string or a list of one to five. The API merges the queries into one flat list and `max_results` is the total across them; the tool says so in its description and in a warning, because no result can be attributed to a query.
- Filters sent as top-level request fields: allow or deny domains (a mixed list is refused locally), recency, publication-date bounds and last-updated bounds (input `YYYY-MM-DD`, sent as `MM/DD/YYYY`), languages, country, `max_results` 1 to 20, `max_tokens` and `max_tokens_per_page`. Everything the probe showed the API accepts wrongly, reports misleadingly or bills for nothing is validated locally before any call.
- Add `PerplexityClient.search(body)` and tolerant response models; a Search POST is never replayed after a response other than 429, and a 429 honors `Retry-After`.
- Record exactly one usage event per Search request that reaches the API: API family `search`, tool `perplexity_search`, cost from `pricing.search_cost_nano` (one billing unit per request however many queries it holds; empty results still billed; failed requests not billed), request id from the response `id`. To avoid a third copy of the recorder sequence, the call sequence of `agent.run_costed` moves into a small shared helper (`costed.py`) that `run_costed` and the new search call both use; `run_costed` keeps its Agent-specific rules.
- Out of scope: `people` search, page snippets (no HTTP endpoint is documented: `content snippets` exists only as a `pplx` CLI command and `/search` is the only search path in the OpenAPI file), contextualized content extraction, search as a tool inside the Agent API, caching of results, streaming, pagination beyond `max_results`, a cost ceiling.

## Capabilities

### New Capabilities

- `search-client`: typed access to the Search API in the client: the `search` call, tolerant response models, retry rules for a billed POST, error mapping for the Search API's flat 400 vocabulary and its diagnostics.
- `search-tool`: the `perplexity_search` tool: arguments and local validation, request building, the result shape, third-party text handling, the per-request cost and its recording, and the recording order.

### Modified Capabilities

None. Checked against the main specs: `usage-recording` already names API family `search`, the computed-cost rule ("a fast Search request reports no cost" stores 1000000 nano-USD) and the one-event-per-call contract, and says nothing about how many functions call the recorder (that wording lives only in `CLAUDE.md`, updated in the documentation group); `perplexity-client` already states the create-POST retry rule for any POST; `server-runtime` needs no setting (a search takes 0.2 to 0.5 s, so the general read timeout applies); `local-storage` "Project resolution" already covers a tool that stores a record (the usage event) by get-or-create.

## Impact

- **Code:** `src/mcp_perplexity_pro/` gains `models/search.py`, `search.py` (option validation, request building, response digestion, the search call), `costed.py` (the shared costed-call sequence), `tools/search.py`; `agent.run_costed` becomes a wrapper over `costed.costed_call`; `client.py` gains `search`; `tools/__init__.py` registers one tool (eight in total). `usage.py`, `pricing.py` and `errors.py` change nothing.
- **Tests:** `tests/test_contract_checks.py` (the recorder call-site audit moves from `agent.run_costed` to `costed.costed_call`, and its category table, secrets and tool-list checks gain the new tool), `tests/test_server.py` (the sorted tool list), `tests/test_recording_order.py` and `tests/test_wiring_one_event_per_call.py` (a fifth costed tool).
- **Specs:** two new capabilities, no MODIFIED requirement.
- **Dependencies, settings, migrations:** none. No migration means the live database is untouched and no new backup appears.
- **Spend:** the tool can spend money. A fast search is $0.001 and the default; a web search is $0.005; nothing local caps a caller's number of calls (the provider rate limit seen is 50 request units per second, a multi-query request consuming one unit per query). The live acceptance task spends about $0.007 (two fast and one web search) with a stop guard at $0.03.
- **Tool surface:** from seven tools to eight. `tools/list` grew from 10564 to about 40.5 KB with the Agent tools; one more tool adds its input and output schema to every session's context, so descriptions stay short and the growth is measured (group 3) and recorded in `design.md` Risks. The CLAUDE.md design target is about nine tools.
- **Fixtures:** `tests/fixtures/search_*.json` (34 captures from 2026-10-09, committed in `63dcb0f`) define the models and every spec scenario that names a recorded response.
- **Risks carried forward:** the cost is always computed (the API reports none), so `perplexity_usage` totals cannot be reconciled against the provider's bill from this server alone; billing of an empty result and of a whitespace-only query is documented ("each successful `POST /search` request") but not observable here; the 429 body of the Search API was not captured (invalid requests do not count toward the limit and a valid burst would have cost more than the probe budget); a multi-query request cannot attribute results to queries; snippets can be large (a default result is up to about 4 KB, twenty results about 23 KB).
