# Design

## Context

See `proposal.md` for motivation and `specs/` for requirements. State that shapes the approach:

- Foundation and usage-log are archived (2026-10-09). The server has a client (`client.py`: `request_json`, retry rules, redacted errors), a closed eleven-value error vocabulary (`errors.py`), a unit of work (`storage/session.py`), project resolution (`storage/projects.py`) and a recorder (`usage.py: record_usage`, `agent_response_status`, `usage_from_agent_response`, `format_usd`) with its caller contract in `CLAUDE.md` "How to record usage" and usage-log design D6/D7. Nothing calls the recorder in production yet; `tests/usage_support.py: costed_call` is the reference pattern.
- The Agent API was probed live on 2026-10-09 (spend about $0.04). The captures are committed as `tests/fixtures/agent_*.json` with sidecars (commit `82c747a`, 28 new files; five older agent fixtures from the foundation stay). Every spec scenario that names "the recorded ..." response uses one of them through `httpx2.MockTransport`. Lesson `docs-lie-probe-the-api-first`: the documentation was wrong or silent on six points (see "Observed shapes").
- `delete_project` deletes from every table with a foreign key to `projects.id` (introspection, no registry) and counts only those rows; rows two hops away go by cascade because `PRAGMA foreign_keys=ON` is set per connection. New tables here are ordinary (CASCADE), not retained.
- Tool modules must not use `from __future__ import annotations`; every tool is `register(server)`, typed with `Annotated[..., Field(description=...)]`, returns `ToolResult(content=..., structured_content=...)` and raises `PerplexityError` for anticipated failures.
- The live server runs under pm2 on port 8102 and must not be touched by development or tests; the live acceptance (group 7) is the one place a human restarts it.

## Goals / Non-Goals

**Goals:**
- A cheap-by-default grounded `ask`, a persisted `chat` and long `research` as a background job, with depth chosen by the caller.
- Every upstream call recorded exactly once through the existing recorder, in the order the contract requires, from a small number of call sites.
- No tool call waits for a long run; no operation can silently lose a result or a cost it could have kept.
- Local validation of every case the probe showed the API accepts wrongly or reports misleadingly.

**Non-Goals:**
- Auto-routing between depths or models, cost ceilings or budgets (the user prefers routing in a later epic; defaults are cheap and descriptions state costs).
- Streaming, the Search, Embeddings and Decisions APIs, profiles, skills, MCP connectors, sandbox and image tools, attachments.
- Pruning chats, jobs or usage events; renaming chats; a `jobs delete`.
- Mapping inline citation markers to sources (the API gives no reliable key, D3).
- Recording spend of runs that nobody ever observes terminal (D8 lists the gap and its mitigation).

## Decisions

**D1. Four tools and one shared helper module.** Names are fixed by the product intent: `perplexity_ask`, `perplexity_chat`, `perplexity_research`, `perplexity_jobs`. Layout: `models/agent.py` (tolerant request-side and response-side pydantic models), `agent.py` (option validation, request building, response digestion, the shared costed-call sequence D4), `tools/ask.py`, `tools/chat.py`, `tools/research.py`, `tools/jobs.py`, three ORM classes in `storage/models.py`, migrations `0003_chats.py` and `0004_research_jobs.py`. `research` and `jobs` are separate tools because one starts spend and the other manages it; a combined tool would have `query` required for one action and forbidden for the rest. Annotations: `ask` `readOnlyHint=False, destructiveHint=False, openWorldHint=True` (it writes usage events and may create a project); `chat` adds `destructiveHint=True` (it has `delete`); `research` like `ask`; `jobs` `destructiveHint=False` (`cancel` stops a run but removes no stored record). *Alternative:* one `perplexity_agent` tool with a mode. Rejected: the descriptions must state different costs and the schema would be a union of unrelated parameter sets.

**D2. Request building is one pure function** (`agent.build_request(options, input, *, store, background, previous_response_id)`), tested against the recorded request shapes (each new sidecar carries its `request`). Rules and the probe evidence behind each:

| Rule | Evidence |
|---|---|
| `depth` -> `{"preset": depth}`; no tools unless a search option is given | `agent_fast_filters` (a preset plus an explicit `web_search` tool keeps the preset's fast-search price, $0.001 per search); `agent_low_fetch_url` (an explicit tool list REPLACES what the preset would have used: no search ran) |
| `model` -> `{"model": m}`, no preset, `tools: [web_search]`, `max_steps: 3` | `agent_model_without_tools` (a model with no tools is ungrounded, $0.00021); the probe's model plus `web_search` plus `max_steps` 3 searched twice for $0.00615, so an explicit model searches at the standard $0.0025 rate, 2.5 times a fast-preset search |
| `depth` with `model` refused, `search` without `model` refused | a preset plus a model is accepted by the API and the preset's search still applies (probe `p5h`), so combining them would silently ignore one of the two options |
| `high` and `xhigh` refused for ask and chat | documented as minutes and dollars; `medium` ran about 35 s (background) |
| Anthropic id -> default `max_output_tokens` 4096 | `agent_anthropic_no_max_output_tokens_400`: "max_output_tokens is required when using Anthropic models". 4096 is a choice (a value the probe accepted was 50), not a measured limit |
| Domain filter: reject mixing allow and deny, cap 20 | docs: "either allowlist or denylist, not both", "up to 20"; the API accepted a mixed list (probe `p7h`) |
| Dates: strict `YYYY-MM-DD` in, `MM/DD/YYYY` out | docs require `MM/DD/YYYY`; the API accepted `2026-09-01` and returned results (probe `p7l`), so the API will not catch a typo |
| `max_results` 1 to 50, `country` 2 letters | docs and the API's `max results must be at least 1` |
| `store: false` for ask and chat | single-turn answers are never refetched; chat continues from a `store:false` response (D6) |
| `input` is always a string (or the replay list), never empty | an empty string is a clear 400, but a number, object, `[]` or a missing `input` all return the misleading "input array cannot be empty" (`p7c`-`p7j`) |
| `max_steps` is never user-settable | the API accepted 101 (`p7p`); the only value we send is 3 |
| `reasoning` is not exposed | `fast` echoes `effort` it was given but cost and latency behavior was not characterized |

*Alternative:* pass an `options` object through to the API. Rejected: it would forward every mistake the probe found; the typed surface is also what keeps the tool schema small.

**D3. Response digestion is one function** (`agent.digest(run)`): `answer` is the text of the last `output_text` part of the last `message` item (empty string if there is none), `sources` come from `search_results.results[]` and `fetch_url_results.contents[]` in output order, de-duplicated by exact URL, each `{url, title, date, id}`. Why not map inline markers: `annotations` is `[]` in every capture; the text contains markdown links, `[1]` or bare `[web:N]` with `N` 0-based while `results[].id` is 1-based, and nothing documents the mapping, so a mapping would be a guess presented as data. Why include fetched pages: `agent_low_fetch_url` has no `search_results` at all, so a search-only list would be empty for an answer that did cite a page. The fetch items carry `title`, `url` and a `snippet` (page text; the probe report said "no page text", the fixture shows a snippet, so the report was wrong here); the snippet is NOT returned, to keep results small. `usage` summary: `usage_from_agent_response(run.usage)` (the same parser the recorder runs, so the result and the stored event agree), `cost_usd = format_usd(cost_nano_usd)` when `cost_source != "none"`, else null. `status`: `completed` or `incomplete` as the API says; `incomplete_reason` from `incomplete_details.reason`. A 200 with `incomplete` is a result with a warning (the run happened and its cost is real); it is NOT an error, otherwise the caller would see a failure for spend that was recorded.

**D4. One costed-call sequence, two `record_usage` call sites.** `agent.run_costed(ctx, *, tool, project, body, preset, background)` does exactly the recorder contract: `validate_project_name` (pure), a short write unit that commits the project, the client call timed with `time.monotonic()`, then on `PerplexityError` `record_usage(status=exc.category)` and re-raise, else `agent_response_status(body)` and, when it is not `None`, `record_usage(... usage=body.get("usage"), model=body.get("model"), preset=preset, request_id=body.get("id"), secrets=(api_key,))`. `ask`, `chat` and the `research` submit call it; their own writes come after it returns. The second call site is the job observation (D8). A mechanical sweep for Gate 2 is `rg "record_usage\(" src/` which must show exactly those two sites. Local validation failures happen before `run_costed`, so they record nothing (no upstream call was made). *Alternative:* each tool inlines the sequence (the usage-log design's example). Rejected: four copies of an order that is the single most failure-prone rule in the codebase (a recorder inside an open write unit silently loses spend, usage-log D6).

**D5. Client changes.** `models/agent.py`: `AgentRun` (`id`, `status` required; `model`, `output`, `usage`, `error`, `incomplete_details` optional; `extra="allow"`), `CancelResponse` (`response_id`, `status`). `PerplexityClient.create_run(body, *, background)`, `get_run(response_id)`, `cancel_run(response_id)` wrap `request_json`, parse with the existing `_parse` (so a missing required field is `unexpected_response` naming path and field) and validate the id against `resp_[A-Za-z0-9_-]{1,100}` before building a path. `request_json` and `_send` gain an optional `timeout` argument; `_timeout_error` reports the effective timeout instead of `self._timeout`. `create_run` passes the agent read timeout (`Settings.agent_read_timeout`, default 120 s; read and write) when `background` is false; every other call keeps the general one (a background submit returned in 0.35 s, a GET in well under a second). The retry rules need no change: `create_run` and `cancel_run` are POSTs (not replayed after a response other than 429, nor after a sent-request timeout), `get_run` is a GET (retried). `x-request-id` is the only request-id header the API sends (`agent_response_headers`: `x-request-id` equals the response id minus `resp_`; no `request-id`), and the client already logs it; nothing to change. The API's error `type` is ignored for the category (400 for `invalid_parameter`, `invalid_model` and `invalid_request` alike), as the existing rule says. The helpers return the model; callers pass `run.model_dump(mode="json")` to `agent_response_status` and `record_usage`.

**D6. Chat: local history is the truth, `previous_response_id` is a shortcut.** Tables (migration `0003`, both `created_at`/`updated_at` naive UTC via `usage.utcnow`):
`chats(id PK, project_id NOT NULL FK projects.id ON DELETE CASCADE, title NOT NULL, created_at, updated_at)` with index `(project_id, updated_at)`; `chat_messages(id PK, chat_id NOT NULL FK chats.id ON DELETE CASCADE, role NOT NULL, content NOT NULL, created_at, response_id, model, preset, sources_json)` with index `(chat_id, id)`. `chats` is an ordinary scoped table, so `delete_project` removes and counts it and the messages go by cascade, uncounted (the foundation's two-hop rule).
Continuation: the anchor is the last assistant message's `response_id`; the request sends only the new message plus `previous_response_id` and `store: false`. Evidence: a `store:false` response was continued once (`agent_continue_store_false`). **What this does not prove**, stated because the parent decision said "for privacy": the documentation says `store: false` "only hides a response from retrieval — it does not disable persistence", so it is NOT a retention control and the tool descriptions must not claim one. It also states a `store:false` response "can still be used as a continuation source". Multi-level chaining and how long a `store:false` anchor lasts are unverified; group 3 carries an explicit live task (three chained turns at depth `fast`, then one more turn the next day) and the spec's `replay` option is the designed answer if it fails, so a failure costs a retry, not the chat. Why chain at all instead of always replaying: the chain sends one message per turn (replay's input grows with every turn, and so does its bill) and the API keeps the search context. Why `store: false` instead of true: nothing here retrieves chat turns; `false` is the choice that cannot be worse for the user.
The API rejects a `previous_response_id` that is unknown, malformed, still in progress or cancelled with the SAME body, `400 {"message":"invalid request","type":"invalid_request"}` (`agent_chat_bad_previous_response_400`, probes `p3c`-`p3h`), which is also the body it returns for an invalid inner JSON schema; a clear message therefore cannot be derived from the API. The tool recognizes exactly that body on a chained send (status 400, type `invalid_request`, message `invalid request`) and replaces it with a message that says the provider could not continue and that `replay` true resends the stored history. It does NOT retry by itself: a hidden second call would double the bill on a transient condition and make the failure harder to see. Only completed turns are stored: an `incomplete` run is returned with a warning (it is recorded and billed) and not saved, so the anchor stays a completed response (the API refuses non-completed anchors, `p3g`, `p3h`) and replay never contains a half answer.
Concurrency: two simultaneous sends to one chat both read the same anchor and both append; the chat then holds two assistant answers to one question, in arrival order. Not prevented (it needs a lock held across an LLM call, or a version check that would discard a billed answer); documented as unsupported use. A new chat is created only in the post-call write unit (D4), so a failed first send leaves nothing.

**D7. Research jobs: our clock, our row.** Table `research_jobs` (migration `0004`): `id PK`, `project_id NOT NULL FK ... ON DELETE CASCADE`, `query TEXT NOT NULL`, `depth NOT NULL`, `response_id NOT NULL UNIQUE`, `status NOT NULL`, `model`, `started_at NOT NULL`, `last_checked_at`, `finished_at`, `cancel_requested_at`, `result_text`, `sources_json`, `incomplete_reason`, `error_text`, `total_tokens`, `cost_nano_usd`, `cost_source`, `usage_recorded INTEGER NOT NULL DEFAULT 0`; indexes `(project_id, id)` and `(status)`. Evidence for "our own times": across one run `created_at` was 1791572935 at submit, 1791572965 on an in-progress GET and 1791572975 on the completed GET, and `completed_at` was null until the last one, where it equals that GET's `created_at` (fixtures `agent_background_submit_medium`, `_in_progress`, `_completed`); the API's timestamps are the time of the request, so persisting them would store the poll time and call it the run time. `model` is the preset NAME (`"medium"`) until completion, so it is stored only from a terminal snapshot. `result_text` and `sources_json` are bounded by the API's own output cap; the usage summary is kept as three columns so `result` needs no re-parse. Job ids are the table's integer id; every action also checks `project_id`, so an id from another project is `not_found` rather than a leak across the project scope the rest of the server keeps. The query and result text are stored locally in a 0600 database the same way chat text is (usage events, by contrast, never store content).
Status vocabulary: `queued`, `in_progress`, `completed`, `cancelled` were observed; `failed` and `incomplete` are documented and unseen for background runs. The terminal set is `{completed, failed, incomplete, cancelled}` plus our own `lost`. Anything else is stored verbatim as non-terminal: a new status the API invents must not stop `status` from working or trigger a premature event, and note that `agent_response_status` returns `unexpected_response` (a recordable result) for an unknown status, which is why the terminal test happens BEFORE it is consulted.

**D8. Recording a background run, and the cancelled decision.** `observe(job, run)` is the second `record_usage` site: when the run's status is terminal and the row has not recorded, call `agent_response_status(run_dict)` (`ok` for completed, `unexpected_response` for failed, incomplete and cancelled, because every one of those has a non-null `error`), then `record_usage` with `tool="perplexity_research"` (the spend belongs to the tool that started the run, whichever `jobs` action observed it, so a report grouped by tool shows research cost under research), `preset=job.depth`, `model` from the snapshot, `request_id=job.response_id`, the job's project name, and `latency_ms` from `started_at` to now (an upper bound: it includes the wait until someone looked). The recorder call happens with no write unit open; the row update (status, model, `finished_at`, result, usage summary, `usage_recorded=1`) is the write unit after it. A crash between them is safe for an `ok` run: the next observation records again and the partial unique index on `(api, request_id)` drops the duplicate; a failed/cancelled run is not covered by that index, so such a crash can double-count one event (accepted, like usage-log D8 edge (c), and narrower than the window already accepted there).
*Changed from the brief:* the brief said a `cancelled` run "has usage null and is not recorded: accepted gap". The capture shows the opposite is the honest choice: the cancelled run's output already held six search results (`agent_background_cancelled`), so tool charges were incurred while `usage` is null. Recording it with status `unexpected_response`, cost 0 and source `none` costs nothing, is the existing contract (`agent_response_status` already says so for any non-null `error`), and makes `perplexity_usage` count the call as unknown cost (`calls_cost_unknown`), which is what its lower-bound wording exists for. Skipping it would require a special case against the recorder's single decision point. Cost: a user-requested cancel adds one to the usage report's `errors`. Reverting is one scenario and one branch.
The gap that stays: a run that nobody observes terminal is never recorded (`perplexity_research` returns, the user never calls `jobs` again). Mitigations: `jobs list` shows `usage_recorded` and `refresh` true settles up to 10 running jobs in one call; the README and tool descriptions say so. Deleting a project with unfinished jobs discards the rows, so their spend is never recorded (the provider keeps running them); the project delete description is unchanged because it already says "its stored records".

**D9. Cancel is read-first.** The API's cancel of an unknown id returns the same `400 "already terminal"` as a cancel of a finished run (`agent_cancel_unknown_400` equals `agent_cancel_terminal_400` byte for byte), so a bare POST cannot tell "too late" from "no such run". `jobs cancel` therefore GETs first (a 404 gives `lost`, a terminal state is reported and observed), POSTs once for a running run and reports `cancelling` (GET never returns `cancelling`; the run turns `cancelled` after a few more in-progress polls). A POST rejected as already terminal means the run finished between the two calls, so it re-fetches once and reports the real state instead of an error. A second cancel on a pending one sends nothing (whether a repeated POST is harmless is unknown). The cancel action never records usage itself; the later observation does.

**D10. Shapes at the tool boundary.** `AskResult` (also the base of the chat send result): `answer`, `answer_json`, `sources[]`, `status`, `incomplete_reason`, `warnings[]`, `model`, `depth`, `response_id`, `usage{input_tokens, output_tokens, total_tokens, cost_usd, cost_source}`, `latency_ms`, `project`. `ChatResult`: `action`, `project`, `chat`, `chats[]`, `messages[]`, `chats_total`, `messages_total`, `truncated`, the `AskResult` fields for `send`, `continuation` (`new`|`chained`|`replay`), `messages_removed`. `ResearchResult`: `job_id`, `response_id`, `status`, `depth`, `project`, `started_at`, `message`. `JobsResult`: `action`, `project`, `job`, `jobs[]`, `jobs_total`, `truncated`, `answer`, `sources[]`, `usage`, `progress{searches, fetches}`, `warnings[]`, `message`, `not_refreshed`. Text content is a short readable rendering (answer first, sources as a numbered list of `title - url`, then one usage line). Money is always the exact string from `format_usd`, never a float.

**D11. Costs in descriptions are evidence, and labelled.** fast: $0.00119 to $0.0018 over the captured fast-preset calls (probe report: about $0.001 to $0.002, 2.4 s); low: $0.00386 (probe report range $0.004 to $0.02, 7.1 s; only the one call is in the fixtures); medium: $0.01599 for the captured run (report range $0.016 to $0.05, about 35 s); high and xhigh were NOT probed, the "up to about $0.4 to $0.9" for high comes from the probe report and the documentation's positioning, and the descriptions say "estimate". There is no cap: a single `high` run can cost more than the whole acceptance budget. Reviewer note: `pricing.py` prices a `fetch_url` invocation at $0.0005, while the captured reported cost was $0.0036 and $0.0035 per invocation (`token_usage` shows the fetch ran its own model calls); it only matters for the `computed` fallback, which the Agent responses never use, but it means a computed fetch cost would understate.

**D12. Settings.** One new setting, `agent_read_timeout` (`PERPLEXITY_AGENT_READ_TIMEOUT`, float, greater than 0, default 120), added to `Settings`, the `--help` text in `cli.py` and the README table; the server-runtime configuration requirement is MODIFIED to list it. 120 s: a synchronous `medium` run took about 35 s, so 120 s leaves 3x headroom; the shutdown drain bound stays 10 s (an in-flight synchronous call that outlives it is abandoned and its event can be lost, the existing accepted edge).

**D13. Tests.** Offline, through `build_server` with a `MockTransport` serving the recorded fixtures (the pattern of `tests/test_usage_e2e.py`), a request-capturing transport to assert the exact request bodies, and the existing mutation-check rule (`docs/lessons/cleanup-tests-must-fail-when-cleanup-is-removed.md`) for: the recorder-order test (record inside a write unit loses the event), the cancel read-first test (remove the GET and the unknown-id case goes wrong), the `store: true` guard on research, and the terminal-once test (remove the `usage_recorded` guard and a failed run double-records). Fixture-to-scenario map: `agent_fast_filters`/`_deny_after` request and sources; `agent_low_fetch_url` fetched sources; `agent_incomplete_truncated` incomplete; `agent_chat_turn_a`/`_b` chaining; `agent_chat_bad_previous_response_400` hint; `agent_continue_store_false` the continuation precondition; `agent_structured_*` the structured paths; `agent_model_without_tools` ungrounded; `agent_background_submit_medium`, `_in_progress`, `_completed`, `_cancelled`, `agent_cancel_*` and `agent_get_*` the job paths; `agent_response_headers` the request id. The live tests (`-m live`) are the apply-time chain check and the acceptance group.

## Risks / Trade-offs

- **`store:false` continuation across levels and time is unverified** (one level verified) -> a live task with three chained turns plus a next-day turn, `replay` as the designed fallback, and a clear error message instead of a silent failure (D6). The documentation also says `store:false` is not a privacy control; descriptions will not claim one.
- **The generic 400 is ambiguous** (`agent_chat_bad_previous_response_400` equals the invalid-inner-schema body) -> the hint is attached only where the context makes one cause overwhelmingly likely (chained send; `json_schema` present) and worded "most likely".
- **No cost ceiling** -> `high`/`xhigh` only via `research`, never default, descriptions state the estimate; reviewers should check that no code path can reach those depths through `ask` or `chat`.
- **Cost figures in descriptions are partly from one sample per depth, and `high` is not measured** -> labelled "approximate"; the usage report shows real spend per tool.
- **A synchronous `medium` call may be cut by an edge timeout** (the API sits behind Cloudflare; its default proxy read timeout is 100 s, not verified for this API) -> the 120 s setting is then moot for runs above 100 s and the call fails `upstream_failure` while possibly billed and unrecorded (the accepted gap of usage-recording). `ask` stops at `medium` for this reason; long runs belong to `research`.
- **Unobserved background runs are never recorded** (D8) -> `refresh`, `usage_recorded` in `list`, documentation.
- **Cancelled runs count as an error with unknown cost in the usage report** (D8, a change from the brief) -> reviewers to confirm; one scenario to revert.
- **Deleting a project with running jobs loses their spend and orphans runs at the provider** -> documented, not prevented (a guard would have to veto deletion).
- **Concurrent sends to one chat interleave** (D6) -> documented as unsupported.
- **Prompts and answers are stored in the local database** (chats, jobs) -> same 0600 file and owner-only directory as everything else; usage events still store no content.
- **A local write failing after a completed call loses the answer to the caller** while the event survives (the recorder contract's design) -> accepted; the error is `storage_busy` and the retry costs another call.
- **`sources` is "what the run touched", not "what the answer cites"** -> documented in the tool description; no marker mapping is offered.
- **The tool surface grows from 3 to 7 tools** -> four typed schemas in every session's context; descriptions kept short, `jobs` and `chat` use one tool each for their actions.

## Migration Plan

1. Land client models and helpers with fixture-based tests; no tool changes yet.
2. Add `ask` (no new table). Add chat with migration `0003`. Add research and jobs with migration `0004`. Each migration takes the automatic backup (`backup-0002.db`, `backup-0003.db`) when upgrading a live database and is reversible; a downgrade drops the new tables and their rows (the README backup section says so, as usage-log did for `usage_events`).
3. Acceptance group: restart pm2 (human), reconnect the `perplexity` MCP server, call each tool at the cheapest depth, read `perplexity_usage`.
4. Rollback: revert the merge; or downgrade `0004` then `0003` with the migration tooling. Provider-side runs already started keep running and billing; nothing local can stop them after the rows are gone.

## Observed shapes (the evidence for the decisions above)

Captured 2026-10-09 (`tests/fixtures/agent_*.json`, sidecars carry the request): all runs resolved to `openai/gpt-6-luna` (including `low` and `medium`, which the catalog comment listed as documentation-only). A response has 32 keys always; `output` holds `search_results` (`queries`, `results[{id (1-based int), url, title, snippet, date, last_updated, source}]`), `fetch_url_results` (`contents[{title, url, snippet}]`) and a final `message` (`content[{type: output_text, text, annotations: []}]`). Usage keys are sparse (absent when zero) and null until completion and on a cancelled run. Error envelope `{"error":{"message","type","code"}}`, `code` the integer status; types seen `invalid_request`, `invalid_parameter`, `invalid_model`, `not_found`. A truncated run is HTTP 200, status `incomplete`, `incomplete_details.reason` `max_output_tokens`, empty `output` (all 16 tokens went to reasoning). Structured output returns raw JSON text; the echoed `text.format` stays `text`. Presets add tools silently (a "reply OK" prompt still searched). Cancel returns `{"response_id", "status": "cancelling"}`; the cancelled snapshot has `error {"code":"cancelled",...}`, `incomplete_details {"reason":"cancelled"}`, partial output and `usage` null. Documentation claims the probe contradicted: mixed allow/deny domains invalid (accepted), `MM/DD/YYYY` only (a `YYYY-MM-DD` date accepted), `max_steps` bounded (101 accepted), `store:false` as a privacy-flavoured setting (documentation itself says it only hides retrieval), `fetch_url` carrying no page text in the probe report (a `snippet` is present). The raw headers sample is `agent_response_headers`: `x-request-id`, `x-ratelimit-limit/remaining/used/reset` (limit 50 seen), a Cloudflare `server` header and cookies (redacted in the fixture).
