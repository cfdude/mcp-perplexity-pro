# Design

## Context

See `proposal.md` for motivation and `specs/` for requirements. State that shapes the approach:

- Foundation and usage-log are archived (2026-10-09). The server has a client (`client.py`: `request_json`, retry rules, redacted errors), a closed eleven-value error vocabulary (`errors.py`), a unit of work (`storage/session.py`), project resolution (`storage/projects.py`) and a recorder (`usage.py: record_usage`, `agent_response_status`, `usage_from_agent_response`, `format_usd`) with its caller contract in `CLAUDE.md` "How to record usage" and usage-log design D6/D7. Nothing calls the recorder in production yet; `tests/usage_support.py: costed_call` is the reference pattern.
- The Agent API was probed live on 2026-10-09 (spend about $0.04). The captures are committed as `tests/fixtures/agent_*.json` with sidecars (commit `82c747a`, 28 new files; five older agent fixtures from the foundation stay). Every spec scenario that names "the recorded ..." response uses one of them through `httpx2.MockTransport`. Lesson `docs-lie-probe-the-api-first`: the documentation was wrong or silent on six points (see "Observed shapes").
- `delete_project` deletes from every table with a foreign key to `projects.id` (introspection, no registry) and counts only those rows; rows two hops away go by cascade because `PRAGMA foreign_keys=ON` is set per connection. New tables here are ordinary (CASCADE), not retained.
- Tool modules must not use `from __future__ import annotations`; every tool is `register(server)`, typed with `Annotated[..., Field(description=...)]`, returns `ToolResult(content=..., structured_content=...)` and raises `PerplexityError` for anticipated failures.
- The live server runs under pm2 on port 8102 and must not be touched by development or tests; the live acceptance (group 7) is the one place a human restarts it.

## Goals / Non-Goals

**Goals:**
- A cheap-by-default grounded `ask`, a persisted `chat` and long `research` as a background job, with depth chosen by the caller.
- Every upstream call recorded exactly once through the existing recorder, in the order the contract requires, from a small number of call sites.
- No tool call waits for a long run; no operation can silently lose a result or a cost it could have kept.
- Local validation of every case the probe showed the API accepts wrongly or reports misleadingly.

**Non-Goals:**
- Auto-routing between depths or models, cost ceilings or budgets (the user prefers routing in a later epic; defaults are cheap and descriptions state costs).
- Streaming, the Search, Embeddings and Decisions APIs, profiles, skills, MCP connectors, sandbox and image tools, attachments.
- Pruning chats, jobs or usage events; renaming chats; a `jobs delete`.
- Mapping inline citation markers to sources (the API gives no reliable key, D3).
- Recording spend of runs that nobody ever observes terminal (D8 lists the gap and its mitigation).

## Decisions

**D1. Four tools and one shared helper module.** Names are fixed by the product intent: `perplexity_ask`, `perplexity_chat`, `perplexity_research`, `perplexity_jobs`. Layout: `models/agent.py` (tolerant request-side and response-side pydantic models), `agent.py` (option validation, request building, response digestion, the shared costed-call sequence D4), `tools/ask.py`, `tools/chat.py`, `tools/research.py`, `tools/jobs.py`, three ORM classes in `storage/models.py`, migrations `0003_chats.py` and `0004_research_jobs.py`. `research` and `jobs` are separate tools because one starts spend and the other manages it; a combined tool would have `query` required for one action and forbidden for the rest. Annotations (all four advertise an output schema and `readOnlyHint=False`, since each writes usage events or rows): `ask` `destructiveHint=False, openWorldHint=True` (it may create a project); `chat` `destructiveHint=True` (it has `delete`); `research` like `ask`; `jobs` `destructiveHint=True` (changed from the first draft's false: `cancel` stops a provider run for good, which cannot be undone and discards the run's remaining output, even though no stored record is removed). Descriptions say what is stored where and never claim provider non-retention (D6, D7). *Alternative:* one `perplexity_agent` tool with a mode. Rejected: the descriptions must state different costs and the schema would be a union of unrelated parameter sets.

**D2. Request building is one pure function** (`agent.build_request(options, input, *, store, background, previous_response_id)`), tested against the recorded request shapes (each new sidecar carries its `request`). Rules and the probe evidence behind each:

| Rule | Evidence |
|---|---|
| `depth` -> `{"preset": depth}`; no tools unless a search option is given | `agent_fast_filters` (a preset plus an explicit `web_search` tool keeps the preset's fast-search price, $0.001 per search); `agent_low_fetch_url` (an explicit tool list REPLACES what the preset would have used: no search ran) |
| `model` -> `{"model": m}`, no preset, `tools: [web_search]`, `max_steps: 3` | `agent_model_without_tools` (a model with no tools is ungrounded, $0.00021); the probe's model plus `web_search` plus `max_steps` 3 searched twice for $0.00615, so an explicit model searches at the standard $0.0025 rate, 2.5 times a fast-preset search |
| `depth` with `model` refused, `search` false without `model` refused (`search` true is accepted everywhere as a no-op) | a preset plus a model is accepted by the API and the preset's search still applies (probe `p5h`), so combining them would silently ignore one of the two options; a preset always searches, so only `search` false can contradict it |
| `high` and `xhigh` refused for ask and chat | documented as minutes and dollars; `medium` ran about 35 s (background) |
| Anthropic id -> default `max_output_tokens` 4096 | `agent_anthropic_no_max_output_tokens_400`: "max_output_tokens is required when using Anthropic models". 4096 is a choice (a value the probe accepted was 50), not a measured limit |
| Domain filter: reject mixing allow and deny, cap 20 | docs: "either allowlist or denylist, not both", "up to 20"; the API accepted a mixed list (probe `p7h`) |
| Dates: strict `YYYY-MM-DD` in, `MM/DD/YYYY` out | docs require `MM/DD/YYYY`; the API accepted `2026-09-01` and returned results (probe `p7l`), so the API will not catch a typo |
| `max_results` 1 to 50, `country` 2 letters | docs and the API's `max results must be at least 1` |
| `store: false` for ask and every chat send (new, chained and replay); `store: true` for research | single-turn answers are never refetched; chat continues from a `store:false` response (D6); a background run with `store:false` cannot be retrieved (`agent_get_store_false_404`), so research must keep it true |
| `input` is always a string (or the replay list), never empty | an empty string is a clear 400, but a number, object, `[]` or a missing `input` all return the misleading "input array cannot be empty" (`p7c`-`p7j`) |
| `max_steps` is never user-settable | the API accepted 101 (`p7p`); the only value we send is 3 |
| Our own sanity caps: `query` and chat `message` at most 20000 characters, `instructions` at most 10000, `max_output_tokens` 1 to 64000 | chosen, not measured, and not provider limits; they keep a single call from carrying an unbounded payload into the local database and the bill |
| Structured output: `response_format` `{"type": "json_schema", "json_schema": {"name": "answer", "schema": <schema>}}`, no `strict` | `agent_structured_output` (name `capital`, no `strict`) and the documentation's example send exactly this shape; `strict` appears in neither and was not probed, so it is not sent |
| An explicit tool list REPLACES the preset's tools | `agent_low_fetch_url`: preset `low` with an explicit `fetch_url` tool ran no search. A filtered ask therefore runs with web search alone (a `medium` ask with a filter loses the preset's page fetching); the tool description says so |
| `reasoning` is not exposed | `fast` echoes `effort` it was given but cost and latency behavior was not characterized |

**How the request tests compare.** The request-equality test builds each request from the options of a sidecar and compares it with the sidecar's `request` plus `store: false` (research: plus `store: true`), minus `reasoning` (the probe sent `reasoning.effort` for `agent_fast_filters`; the tool never does) and, for the structured sidecar only, with `json_schema.name` compared against the constant `answer` instead of the probe's `capital`. Shapes without a sidecar (Anthropic with and without a cap, an explicit model with `web_search` and `max_steps` 3) are asserted from inline expected dicts written in the test; nothing recorded backs them, and the tests say so.

*Alternative:* pass an `options` object through to the API. Rejected: it would forward every mistake the probe found; the typed surface is also what keeps the tool schema small.

**D3. Response digestion is one function** (`agent.digest(run)`): `answer` is the text of the last `output_text` part of the last `message` item (empty string if there is none), `sources` come from `search_results.results[]` and `fetch_url_results.contents[]` in output order, de-duplicated by exact URL, each `{url, title, date, id}`. Why not map inline markers: `annotations` is `[]` in every capture; the text contains markdown links, `[1]` or bare `[web:N]` with `N` 0-based while `results[].id` is 1-based, and nothing documents the mapping, so a mapping would be a guess presented as data. Why include fetched pages: `agent_low_fetch_url` has no `search_results` at all, so a search-only list would be empty for an answer that did cite a page. The fetch items carry `title`, `url` and a `snippet` (page text; the probe report said "no page text", the fixture shows a snippet, so the report was wrong here); the snippet is NOT returned, to keep results small. `usage` summary: `usage_from_agent_response(run.usage)` (the same parser the recorder runs, so the result and the stored event agree), `cost_usd = format_usd(cost_nano_usd)` when `cost_source != "none"`, else null. `status`: `completed` or `incomplete` as the API says; `incomplete_reason` from `incomplete_details.reason`. A 200 with `incomplete` is a result with a warning (the run happened and its cost is real); it is NOT an error, otherwise the caller would see a failure for spend that was recorded. Any other 200 status (`failed`, `cancelled`, `queued`, `in_progress`, an unknown one) or a non-null `error` on a `completed` body is an `unexpected_response` naming the (redacted, capped) status, raised AFTER `run_costed` recorded it by its usual rule (an event for terminal failures, none for `queued` or `in_progress`). `digest` never raises on a malformed body: `AgentRun.output` is typed `Any` (D5), so a non-list value reaches it and yields an empty answer.

**D4. One costed-call sequence, two `record_usage` call sites.** `agent.run_costed(ctx, *, tool, project, body, preset, background)` does exactly the recorder contract: `validate_project_name` (pure), a short write unit that commits the project (skipped by a chat send that names a `chat_id`, which has already found its project, D15), the client call timed with `time.monotonic()`, then on `PerplexityError` `record_usage(status=exc.category)` and re-raise, else `agent_response_status(body)` and, when it is not `None`, `record_usage(... usage=body.get("usage"), model=body.get("model"), preset=preset, request_id=body.get("id"), secrets=(api_key,))`. `ask`, `chat` and the `research` submit call it; their own writes come after it returns. The second call site is the job observation (D8). A mechanical sweep for Gate 2 is `rg "record_usage\(" src/` which must show exactly those two sites. For a background submit `run_costed` records only a terminal body (`completed`, `failed`, `incomplete`, `cancelled`, or any status with a non-null `error`); a `queued`, `in_progress` or unknown status is returned unrecorded, because `agent_response_status` would call an unknown status an `unexpected_response` and spend a dedupe-free event on a run that has not finished. A call cut at the edge (a Cloudflare read timeout, a dropped connection) surfaces as `network_timeout` or `upstream_failure` and IS recorded as a failure event with cost unknown; only a task cancelled in the middle of the call (the client went away, the server is stopping) raises no `PerplexityError` and records nothing. Local validation failures happen before `run_costed`, so they record nothing (no upstream call was made). *Alternative:* each tool inlines the sequence (the usage-log design's example). Rejected: four copies of an order that is the single most failure-prone rule in the codebase (a recorder inside an open write unit silently loses spend, usage-log D6).

**D5. Client changes.** `models/agent.py`: `AgentRun` (`id`, `status` required; `model`, `output`, `usage`, `error`, `incomplete_details` optional; `output` typed `Any` with default `[]` so that a non-list value from the API is kept for `digest` instead of failing the parse; `extra="allow"`), `CancelResponse` (`response_id`, `status`). `PerplexityClient.create_run(body, *, background)`, `get_run(response_id)`, `cancel_run(response_id)` wrap `request_json`, parse with the existing `_parse` (so a missing required field is `unexpected_response` naming path and field) and validate the id against `resp_[A-Za-z0-9_-]{1,100}` before building a path. `request_json` and `_send` gain an optional `timeout` argument; `_timeout_error` reports the effective timeout instead of `self._timeout`. `create_run` passes the agent read timeout (`Settings.agent_read_timeout`, default 120 s; read and write) when `background` is false; every other call keeps the general one (a background submit returned in 0.35 s, a GET in well under a second). The retry rules need no change: `create_run` and `cancel_run` are POSTs (not replayed after a response other than 429, nor after a sent-request timeout), `get_run` is a GET (retried). `x-request-id` is the only request-id header the API sends (`agent_response_headers`: `x-request-id` equals the response id minus `resp_`; no `request-id`), and the client already logs it; nothing to change. The API's error `type` is ignored for the category (400 for `invalid_parameter`, `invalid_model` and `invalid_request` alike), as the existing rule says. `PerplexityError` gains `api_message` (the text of `error.message`, redacted, without the readable message's `(type: ...)` suffix), set by `error_from_response`: the chat tool's exact-body recognition (D6) needs the raw text, and `exc.args[0]` carries the suffix. The helpers return the model; callers pass `run.model_dump(mode="json")` to `agent_response_status` and `record_usage`.

**D6. Chat: local history is the truth, `previous_response_id` is a shortcut.** Tables (migration `0003`, both `created_at`/`updated_at` naive UTC via `usage.utcnow`):
`chats(id PK AUTOINCREMENT, project_id NOT NULL FK projects.id ON DELETE CASCADE, title NOT NULL, created_at, updated_at)` with index `(project_id, updated_at)`; `chat_messages(id PK, chat_id NOT NULL FK chats.id ON DELETE CASCADE, role NOT NULL, content NOT NULL, created_at, response_id, model, preset, sources_json)` with index `(chat_id, id)`. `chats` is an ordinary scoped table, so `delete_project` removes and counts it and the messages go by cascade, uncounted (the foundation's two-hop rule).
Continuation: the anchor is the last assistant message's `response_id`; the request sends only the new message plus `previous_response_id` and `store: false` (every send sets `store: false`: new, chained and replay). Evidence: a `store:false` response was continued once (`agent_continue_store_false`). **What this does not prove**, stated because the parent decision said "for privacy": the documentation says `store: false` "only hides a response from retrieval — it does not disable persistence", so it is NOT a retention control and the tool descriptions must not claim one. It also states a `store:false` response "can still be used as a continuation source". Multi-level chaining and how long a `store:false` anchor lasts are unverified; group 3 carries an explicit live task (three chained turns, the second at depth `low`, a replay turn, then one more turn the next day) and the spec's `replay` option is the designed answer if it fails, so a failure costs a retry, not the chat. Why chain at all instead of always replaying: the chain sends one message per turn (replay's input grows with every turn, and so does its bill) and the API keeps the search context. Why `store: false` instead of true: nothing here retrieves chat turns; `false` is the choice that cannot be worse for the user. The tool description says local storage holds the messages and that `store` false hides retrieval only.
The API rejects a `previous_response_id` that is unknown, malformed, still in progress or cancelled with the SAME body, `400 {"message":"invalid request","type":"invalid_request"}` (`agent_chat_bad_previous_response_400`, probes `p3c`-`p3h`), which is also the body it returns for an invalid inner JSON schema; a clear message therefore cannot be derived from the API. The tool recognizes exactly that body on a chained send (status 400, `api_type` `invalid_request`, `api_message` equal to `invalid request`) and replaces it with a message that says the provider could not continue and that `replay` true resends the stored history. It does NOT retry by itself: a hidden second call would double the bill on a transient condition and make the failure harder to see. Only completed turns are stored: an `incomplete` run is returned with a warning (it is recorded and billed) and not saved, so the anchor stays a completed response (the API refuses non-completed anchors, `p3g`, `p3h`) and replay never contains a half answer; an incomplete FIRST send creates no chat (`chat_id` null, `continuation` `new`). Any other status or an error on a 200 is an `unexpected_response` (D3) and stores nothing.
**Replay input shape.** Pinned from the API's conversation-state page and quickstart (fetched 2026-10-09): `input` is a list of `{"type": "message", "role": "user" | "assistant", "content": "<string>"}` items, user and assistant text as plain strings (the typed-part form `[{"type": "output_text", ...}]` is not used). The offline test asserts exactly this; group 3's live task saves a real replay request and response as scrubbed fixtures with sidecars, so the shape stops being documentation-only. A replay whose stored text exceeds 100000 characters still runs and adds a warning (it resends everything on every turn).
**Depth switch on a chain is unprobed.** The spec lets a turn name a different preset than the one that produced the anchor; no capture shows the API accepting that, so the live task includes one switch (`fast` then `low`) and its outcome is recorded here.
**Local failures after a billed call.** The chat write runs after the event is recorded. If it fails (busy database, disk), the result is still returned with a `not_saved` warning: the money is spent and the caller has the answer, so raising would hide it; the next send chains from the older anchor. An integrity failure (the chat or its project was deleted while the call ran) cannot be fixed by retrying, so it maps to `not_found`, not `storage_busy`. `chats` and `research_jobs` are created with `sqlite_autoincrement` so that deleting the newest chat does not let the next one reuse its id and a stale `chat_id` silently append to a different conversation.
**Project lookup.** See D15: `list`, `read`, `delete` and a send with `chat_id` look the project up and never create it; a send with `chat_id` resolves the project only after it has found the chat.
Concurrency: two simultaneous sends to one chat both read the same anchor and both append; the chat then holds two assistant answers to one question, in arrival order. Not prevented (it needs a lock held across an LLM call, or a version check that would discard a billed answer); documented as unsupported use. A new chat is created only in the post-call write unit (D4), so a failed first send leaves nothing.

**D7. Research jobs: our clock, our row.** Table `research_jobs` (migration `0004`): `id PK AUTOINCREMENT`, `project_id NOT NULL FK ... ON DELETE CASCADE`, `query TEXT NOT NULL`, `depth NOT NULL`, `response_id NOT NULL UNIQUE`, `status NOT NULL`, `model`, `started_at NOT NULL`, `last_checked_at`, `finished_at`, `cancel_requested_at`, `missing_since`, `result_text`, `sources_json`, `incomplete_reason`, `error_text`, `input_tokens`, `output_tokens`, `total_tokens`, `cost_nano_usd`, `cost_source`, `usage_recorded INTEGER NOT NULL DEFAULT 0`; indexes `(project_id, id)` and `(status)`. Evidence for "our own times": across one run `created_at` was 1791572935 at submit, 1791572965 on an in-progress GET and 1791572975 on the completed GET, and `completed_at` was null until the last one, where it equals that GET's `created_at` (fixtures `agent_background_submit_medium`, `_in_progress`, `_completed`); the API's timestamps are the time of the request, so persisting them would store the poll time and call it the run time. `model` is the preset NAME (`"medium"`) on queued, in-progress AND cancelled snapshots (fixtures `agent_background_submit_medium`, `_in_progress`, `_cancelled`); only the completed snapshot carries the resolved model. The rule: store and record `model` when the snapshot is `completed`, or when its value contains `/` and differs from the job's depth; otherwise it stays null. `result_text` and `sources_json` are bounded by the API's own output cap; the usage summary is kept as five columns (`input_tokens`, `output_tokens`, `total_tokens`, `cost_nano_usd`, `cost_source`) so `jobs result` fills the same `UsageSummary` as `ask` (D10) without re-parsing; the migration adds `input_tokens` and `output_tokens` for that reason. `missing_since` records the first fetch the provider answered 404 (below). Job ids are the table's integer id (never reused); every action also checks `project_id`, so an id from another project is `not_found` rather than a leak across the project scope the rest of the server keeps, and no jobs action creates a project (D15). The query and result text are stored locally in a 0600 database the same way chat text is (usage events, by contrast, never store content).
Status vocabulary: `queued`, `in_progress`, `completed`, `cancelled` were observed; `failed` and `incomplete` are documented and unseen for background runs. The terminal set is `{completed, failed, incomplete, cancelled}` plus our own `lost`; a non-null `error` is terminal whatever the status (such a snapshot is stored as `failed` unless its status is already `failed`, `incomplete` or `cancelled`, so the stored status always belongs to the vocabulary the terminal test knows). Anything else is stored verbatim (redacted, cut to 64 characters, D14) as non-terminal: a new status the API invents must not stop `status` from working or trigger a premature event, and note that `agent_response_status` returns `unexpected_response` (a recordable result) for an unknown status, which is why the terminal test happens BEFORE it is consulted. The same terminal test applies to a submit response (D4, D8).
**Lost runs.** A 404 on a fetch of a non-terminal job is not proof the run is gone (the API gave the same 404 for a `store:false` response, `agent_get_store_false_404`, and propagation delay right after a submit is possible). The first 404 sets `missing_since`, leaves the job running and warns; a later 404 marks the job `lost` only when the run was submitted at least 10 minutes earlier (10 is a chosen margin for propagation, not a measurement); any successful fetch clears `missing_since`. A `lost` job records nothing.
**Which jobs `refresh` observes.** Non-terminal jobs of the project ordered by `last_checked_at` ascending, never-checked first, ties by job id ascending, at most 10; `last_checked_at` moves on every successful fetch, so repeated refreshes rotate through a long backlog.

**D8. Recording a background run, and the cancelled decision.** `observe(job_id)` is the second `record_usage` site. It takes the job's in-process `asyncio.Lock` (one per job id, created on demand and dropped when unused), RE-READS the row, and returns the stored state when the row is already terminal or `usage_recorded`; otherwise it fetches, and when the run's status is terminal (D7's test) and the row has not recorded, calls `agent_response_status(run_dict)` (`ok` for completed with a null `error`, `unexpected_response` for every other terminal status and for any non-null `error`), then `record_usage` with `tool="perplexity_research"` (the spend belongs to the tool that started the run, whichever `jobs` action observed it, so a report grouped by tool shows research cost under research), `preset=job.depth`, `model` from the snapshot, `request_id=job.response_id`, the job's project name, and `latency_ms` from `started_at` to now (an upper bound: it includes the wait until someone looked). The recorder call happens with no write unit open; the row update (status, model by the D7 rule, `finished_at`, result, usage summary, `usage_recorded=1`) is the write unit after it. **An observation is two units of work and no two jobs' observations share one**: the usage event (the recorder's own unit, no write unit open) and then the row update. A call that observes several jobs (`jobs list refresh`; cancel's fetch, POST bookkeeping and refetch) commits each in turn, and a later failure rolls back only the failing observation's row update (its event stays, the existing usage-recording exception). This contradicts the main `local-storage` requirements "All-or-nothing tool calls" (one unit of work per call) and "Project resolution" (get-or-create for every call), so this change MODIFIES both in `specs/local-storage/spec.md`: the first allows per-observation commits, the second names by-id actions as look-up-only (D15). A failed fetch (or failed update) in `refresh` is a warning naming the job id and the error category; the list is still returned and the job counts in `not_refreshed` together with the jobs beyond the cap of 10. In `status`, `result` and `cancel` the error propagates, and observations already committed stay. **Concurrency:** the lock serializes overlapping `status`, `list` refresh and `cancel` calls on one job, and the terminal test is repeated after the lock is taken, so they record ONE event whatever the status; the partial unique index on `(api, request_id)` covers `ok` events only, so for a failed, incomplete or cancelled run the lock is the only thing preventing a double event. It is in-process, which is enough because the server is one process (pm2 runs one instance on 8102); a second process on the same database would reintroduce the window, the accepted edge below. A crash between them is safe for an `ok` run: the next observation records again and the partial unique index on `(api, request_id)` drops the duplicate; a failed/cancelled run is not covered by that index, so such a crash can double-count one event (accepted, like usage-log D8 edge (c), and narrower than the window already accepted there).
*Changed from the brief:* the brief said a `cancelled` run "has usage null and is not recorded: accepted gap". The capture shows the opposite is the honest choice: the cancelled run's output already held six search results (`agent_background_cancelled`), so tool charges were incurred while `usage` is null. Recording it with status `unexpected_response`, cost 0, source `none` and NO model (the snapshot's `model` is the preset name, D7) costs nothing, is the existing contract (`agent_response_status` already says so for any non-null `error`), and makes `perplexity_usage` count the call as unknown cost (`calls_cost_unknown`), which is what its lower-bound wording exists for. Skipping it would require a special case against the recorder's single decision point. Cost: a user-requested cancel adds one to the usage report's `errors`. Reverting is one scenario and one branch.
**A submit that comes back terminal** (an instant failure, or a run so short it completed) creates the row as terminal with its result, is recorded ONCE by `run_costed` (D4) and is stored with `usage_recorded=1`, so no observation records it again; a submit with any other status is stored verbatim as running and unrecorded.
**Orphaned run.** The row is written after the provider accepted the run, so an insert failure would leave a billed run with no local handle. The API's response id is first checked against `resp_[A-Za-z0-9_-]{1,100}` (else `unexpected_response`, no row); the insert is retried once; on the final failure the id (redacted, it is not a secret) is logged at ERROR and placed in the error message with the sentence that the run can be cancelled by hand, and the error keeps the mapped category (`storage_busy`, or `internal_error`). The run's spend then stays unrecorded, the existing gap.
The gap that stays: a run that nobody observes terminal is never recorded (`perplexity_research` returns, the user never calls `jobs` again). Mitigations: `jobs list` shows `usage_recorded` and `refresh` true settles up to 10 running jobs in one call; the README and tool descriptions say so. Deleting a project with unfinished jobs discards the rows, so their spend is never recorded (the provider keeps running them); the project delete description is unchanged because it already says "its stored records".

**D9. Cancel is read-first.** The API's cancel of an unknown id returns the same `400 "already terminal"` as a cancel of a finished run (`agent_cancel_unknown_400` equals `agent_cancel_terminal_400` byte for byte), so a bare POST cannot tell "too late" from "no such run". `jobs cancel` therefore GETs first (a 404 follows the lost-run rule of D7 and sends no POST; a terminal state is reported and observed), POSTs once for a running run and reports `cancelling` (GET never returns `cancelling`; the run turns `cancelled` after a few more in-progress polls). A POST rejected as already terminal means the run finished between the two calls, so it re-fetches once and reports the real state instead of an error. **A repeated cancel on a job whose cancel is pending still GETs**, because that GET is where a cancel that has since completed is observed (and recorded); only the second POST is skipped (whether a repeated POST is harmless is unknown). If the write of `cancel_requested_at` fails after the API accepted the cancel, the result is still returned, with a `not_saved` warning. The cancel action never records usage itself; the observation inside it (fetch, refetch) and later ones do, each as its own unit of work (D8).

**D10. Shapes at the tool boundary.** `UsageSummary{input_tokens, output_tokens, total_tokens, cost_usd, cost_source}` is ONE model shared by ask, chat and jobs (jobs fills it from the stored columns, D7). `AskResult` (also the base of the chat send result): `answer`, `answer_json`, `sources[]`, `status`, `incomplete_reason`, `warnings[]`, `model`, `depth`, `response_id`, `usage: UsageSummary`, `latency_ms`, `project`. `ChatResult`: `action`, `project`, `chat_id`, `chat`, `chats[]`, `messages[]`, `chats_total`, `messages_total`, `truncated`, the `AskResult` fields for `send`, `continuation` (`new`|`chained`|`replay`), `messages_removed`. **Pinned names:** top-level `chat_id` is the chat the action concerns (the new chat for a first send, the named chat otherwise) and is null for `list` and for an incomplete first send; `chat` and the records of `chats[]` carry that chat's `id`, `title` and counts. `ResearchResult`: `job_id`, `response_id`, `status`, `depth`, `project`, `started_at`, `message`. `JobsResult`: `action`, `project`, `job_id`, `status`, `job`, `jobs[]`, `jobs_total`, `truncated`, `answer`, `sources[]`, `usage: UsageSummary`, `progress{searches, fetches}`, `warnings[]`, `message`, `not_refreshed` (jobs beyond the cap of 10 plus jobs whose observation failed). **Pinned names:** top-level `job_id` is the job the action concerns (null for `list`), and the `job` record and every record of `jobs[]` also carry their own `job_id` (the table's integer id); top-level `status` is the state the ACTION reports for that job (null for `list`): `queued`, `in_progress`, `completed`, `failed`, `incomplete`, `cancelled`, `lost`, `cancelling`, or an unknown API status verbatim (redacted, cut to 64 characters). `cancelling` is only ever reported by `cancel`, never stored; the stored `status` of the `job` record is the stored one (a cancel that was accepted leaves it running until a fetch shows `cancelled`). Scenarios say "the result's status" for the top-level field and "the job's status" for the stored one. Text content is a short readable rendering (answer first, sources as a numbered list of `title - url`, then one usage line). Money is always the exact string from `format_usd`, never a float.

**D11. Costs in descriptions are evidence, and labelled.** fast: $0.00119 to $0.0018 over the captured fast-preset calls (probe report: about $0.001 to $0.002, 2.4 s); low: $0.00386 (probe report range $0.004 to $0.02, 7.1 s; only the one call is in the fixtures); medium: $0.01599 for the captured run (report range $0.016 to $0.05, about 35 s); high and xhigh were NOT probed, the "up to about $0.4 to $0.9" for high comes from the probe report and the documentation's positioning, and the descriptions say "estimate". There is no cap: a single `high` run can cost more than the whole acceptance budget. Reviewer note: `pricing.py` prices a `fetch_url` invocation at $0.0005, while the captured reported cost was $0.0036 and $0.0035 per invocation (`token_usage` shows the fetch ran its own model calls); it only matters for the `computed` fallback, which the Agent responses never use, but it means a computed fetch cost would understate.

**D12. Settings.** One new setting, `agent_read_timeout` (`PERPLEXITY_AGENT_READ_TIMEOUT`, float, greater than 0, default 120), added to `Settings`, the `--help` text in `cli.py` and the README table; the server-runtime configuration requirement is MODIFIED to list it. 120 s: a synchronous `medium` run took about 35 s, so 120 s leaves 3x headroom; the shutdown drain bound stays 10 s (an in-flight synchronous call that outlives it is cancelled and records nothing, the existing accepted edge; a call merely cut at the network edge is a failure event, D4).

**D13. Tests.** Offline, through `build_server` with a `MockTransport` serving the recorded fixtures (the pattern of `tests/test_usage_e2e.py`), a request-capturing transport to assert the exact request bodies, and the existing mutation-check rule (`docs/lessons/cleanup-tests-must-fail-when-cleanup-is-removed.md`) for: the recorder-order test (record inside a write unit loses the event), the cancel read-first test (remove the GET and the unknown-id case goes wrong), the `store: true` guard on research, the concurrent-observation test (remove the per-job lock and two overlapping `status` calls on a cancelled run record two events, since the dedupe index does not cover non-`ok` events), and the re-record test (drop the partial unique index and an `ok` run observed again after a failed row update shows two events). The `usage_recorded` guard gets no mutation check against ordinary flows: the flag is set in the same row update that makes the status terminal, so removing the guard changes nothing a reachable state can show; only a row seeded directly as non-terminal with `usage_recorded` 1 reaches it (observation must make no fetch and record nothing). Fixture-to-scenario map: `agent_fast_filters`/`_deny_after` request and sources; `agent_low_fetch_url` fetched sources; `agent_incomplete_truncated` incomplete; `agent_chat_turn_a`/`_b` chaining; `agent_chat_bad_previous_response_400` hint; `agent_continue_store_false` the continuation precondition; `agent_structured_*` the structured paths; `agent_model_without_tools` ungrounded; `agent_background_submit_medium`, `_in_progress`, `_completed`, `_cancelled`, `agent_cancel_*` and `agent_get_*` the job paths; `agent_response_headers` the request id. The live tests (`-m live`) are the apply-time chain check and the acceptance group.

**D14. Redaction and caps for upstream text.** Every string that comes from the API and is stored or returned (a status shown verbatim, `incomplete_reason`, error text, warnings built from them, a job's error) passes through `redact_text` with the configured key as a secret and is cut AFTER redaction (64 characters for a status, 200 for a reason, 2000 for an error text), the same order the recorder uses so a key straddling a cut leaves no fragment. User query text, instructions, chat messages and titles, the model's answer and the sources' titles and URLs are CONTENT, stored and returned as they are: redacting an answer that quotes a `pplx-` example would corrupt it. Task 5.3's check is worded to match: the exact key must not appear anywhere in a result, log record or row, and key-shaped tokens only inside those content fields. The main `server-runtime` "Secrets are never emitted" requirement said no key-shaped string anywhere, which would forbid storing a caller's own example, so this change MODIFIES it to bar the configured key everywhere and key-shaped tokens from server-originated text only.

**D15. Project lookup versus creation.** (The main `local-storage` "Project resolution" requirement is MODIFIED to say this; see `specs/local-storage/spec.md`.) Only actions that store something create a project: `ask` and `research` (via `run_costed`, which commits the project before the call) and a chat `send` that starts a chat. Chat `list`, `read`, `delete`, a `send` with `chat_id`, and every `jobs` action call a read-only lookup that never creates it: a list in an absent project is empty with total 0 (a fresh install has no `default` project until something stores to it), and a by-id action is `not_found`. A send with `chat_id` finds the project, then the chat inside it, before any upstream call, and does not run the create step at all.

## Risks / Trade-offs

- **`store:false` continuation across levels and time is unverified** (one level verified) -> a live task with three chained turns (one depth switch), a replay turn and a next-day turn, `replay` as the designed fallback, and a clear error message instead of a silent failure (D6). The documentation also says `store:false` is not a privacy control; descriptions will not claim one.
- **The generic 400 is ambiguous** (`agent_chat_bad_previous_response_400` equals the invalid-inner-schema body) -> the hint is attached only where the context makes one cause overwhelmingly likely (chained send; `json_schema` present) and worded "most likely".
- **No cost ceiling** -> `high`/`xhigh` only via `research`, never default, descriptions state the estimate; reviewers should check that no code path can reach those depths through `ask` or `chat`.
- **Cost figures in descriptions are partly from one sample per depth, and `high` is not measured** -> labelled "approximate"; the usage report shows real spend per tool.
- **A synchronous `medium` call may be cut by an edge timeout** (the API sits behind Cloudflare; its default proxy read timeout is 100 s, not verified for this API) -> the 120 s setting is then moot for runs above 100 s and the call fails `upstream_failure` (or `network_timeout`) while possibly billed. It IS recorded, as a failure event with cost unknown, so the usage report counts it as an unknown-cost call; only a task cancelled mid-call leaves no event. `ask` stops at `medium` for this reason; long runs belong to `research`.
- **Unobserved background runs are never recorded** (D8) -> `refresh`, `usage_recorded` in `list`, documentation.
- **Cancelled runs count as an error with unknown cost in the usage report** (D8, a change from the brief) -> reviewers to confirm; one scenario to revert.
- **Deleting a project with running jobs loses their spend and orphans runs at the provider** -> documented, not prevented (a guard would have to veto deletion).
- **Concurrent sends to one chat interleave** (D6) -> documented as unsupported.
- **The per-job lock is in-process** (D8) -> sufficient for the single pm2 instance; a second server process on the same database could double-record a non-`ok` run (accepted).
- **A job observed only by a 404 may stay unresolved for 10 minutes** (D7) -> deliberate; a `lost` verdict on a transient 404 would stop recording a billed run.
- **Prompts and answers are stored in the local database** (chats, jobs) -> same 0600 file and owner-only directory as everything else; usage events still store no content.
- **A local write failing after a completed call** -> for `chat` the result is returned with a `not_saved` warning (the turn is not stored, the event survives); for a research submit the row is retried once and the response id is logged and put in the error (D8); a chat deleted mid-send gives `not_found` and the billed answer is not returned (accepted: a rare race, the event records the spend).
- **`sources` is "what the run touched", not "what the answer cites"** -> documented in the tool description; no marker mapping is offered.
- **The tool surface grows from 3 to 7 tools** -> four typed schemas in every session's context; descriptions kept short, `jobs` and `chat` use one tool each for their actions.

## Migration Plan

1. Land client models and helpers with fixture-based tests; no tool changes yet.
2. Add `ask` (no new table). Add chat with migration `0003`. Add research and jobs with migration `0004`. The migration tooling takes ONE backup per startup, named for the revision the database STARTED from, so a live revision-0002 database goes straight to head and leaves only `backup-0002.db` (no `backup-0003.db`; that name appears only when a revision-0003 database is upgraded to 0004, which a test covers). Both migrations are reversible; a downgrade drops the new tables and their rows (the README backup section says so, as usage-log did for `usage_events`).
3. Acceptance group: restart pm2 (human), reconnect the `perplexity` MCP server, call each tool at the cheapest depth, read `perplexity_usage`.
4. Rollback: revert the merge; or downgrade `0004` then `0003` with the migration tooling. Provider-side runs already started keep running and billing; nothing local can stop them after the rows are gone.

## Open Questions

- Whether `jobs refresh` should poll all running jobs rather than 10 (answerable after real usage shows how many accumulate; does not change the specs' shape).
- Starvation: `last_checked_at` moves only on a successful fetch, so 10 or more jobs whose fetches keep failing stay at the head of the order and are retried every refresh while healthy jobs behind them are never reached. Moving `last_checked_at` on failed attempts too would fix it at the price of one more write per failure; left open until a real backlog shows it.
