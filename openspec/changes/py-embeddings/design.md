## Context

Search and Decisions reused `costed.costed_call` and a computed cost. Embeddings differs in three ways that shape this change: the API **reports** its cost (so a parser joins `usage._PARSERS`, the first since `agent`), the useful result is not returned to the caller but kept locally (a vector store, new storage), and one logical operation (`index`) may need several upstream requests. Everything else (tolerant parsing, local validation first, no replay of a billed POST, one event per request, recording order) follows the Search and Decisions pattern.

## Goals / Non-Goals

**Goals:** one tool `perplexity_embed` (`index`, `search`, `status`, `delete`); a small project-scoped vector store with cascades; exact decoding of both encodings; the reported cost recorded to the nano-USD; one usage event per upstream request; vectors never returned.

**Non-Goals:** contextualized embeddings, returning or exporting vectors, approximate-nearest-neighbour indexes, re-ranking, images, auto-indexing, indexing the usage log, cost ceilings, a header-based request id (the client exposes no headers).

## Decisions

**D1. One tool, four actions, ten tools.** `perplexity_embed` with `action` `index | search | status | delete`, because the four share the store, the model/dimensions/encoding settings and the privacy wording, and a second tool would cost every session's context twice (CLAUDE.md: prefer one tool with an `action`). Layout: `models/embeddings.py` (`EmbeddingsResponse`), `embeddings.py` (options, validation, chunking, decode, scoring, `embeddings_usage`, `run_embed`), `storage/embeddings.py` (row operations, no network), `tools/embeddings.py`, migration `0005`. Annotations: `readOnlyHint` false, `destructiveHint` true (delete), `openWorldHint` true (index and search call an external API). The tool count reaches ten, one over the CLAUDE.md target of about nine; measured in group 4 and recorded in Risks.

**D2. Request building is one pure function `build_request`**, rules and probe evidence:

| Rule | Evidence |
|---|---|
| `model` is `pplx-embed-v1-0.6b` (default) or `pplx-embed-v1-4b`, always sent | `embeddings_missing_model_400` (`model is required`), `embeddings_unknown_model_400` (`model must be one of: ...`) |
| `dimensions`: an integer, a multiple of 8, 128 to 1024 for `0.6b`, 128 to 2560 for `4b`; when omitted it is NOT sent and the model's full size applies (1024 and 2560); the stored `dimensions` is the size actually returned | `embeddings_dim_64_400`, `embeddings_dim_2000_06b_400`, `embeddings_dim_5000_400`, `embeddings_dim_odd_06b` (`Output dimension must be a multiple of 8, got 130`); the full sizes from `embeddings_single_06b` (1024 bytes decoded) and `embeddings_4b_default_dims` (2560) |
| `encoding_format` is `base64_int8` (tool `encoding` `int8`, default) or `base64_binary` (tool `binary`); always sent | `embeddings_bad_format_400` (`encoding format must be one of: base64_int8 base64_binary`); both decode to `dimensions` and `dimensions / 8` bytes (`embeddings_binary_06b`: 32 bytes for 256 dimensions) |
| `input` is a list of 1 to 64 non-empty strings (our batch cap; the API allows 512), each at most 4000 characters (our chunk size; the API allows 32K tokens each and 120000 per request) | `embeddings_empty_string_400`, `embeddings_empty_in_array_400` (`input[1] cannot be an empty string`), `embeddings_empty_array_400`, `embeddings_513_inputs_400` (`input array exceeds maximum of 512 items`), `embeddings_non_string_input_400`; `embeddings_64_inputs_4000_chars` (64 chunks, 42550 tokens, 200) and `embeddings_100_inputs_5000_chars` (82990 tokens, 200) show the 64 by 4000 batch is far from the limits |
| nothing else is sent | `embeddings_unknown_field_accepted` (an unknown field is accepted and billed) |

**D3. Chunking.** A text is split into chunks of at most 4000 characters (our size, about 1000 tokens, so 64 chunks are about 64k tokens in the worst case, under the 120000-token limit): at the last blank line, else the last line break, else the last space before the limit, else at the limit; chunks are stripped and empty ones dropped; a text yields at most 50 chunks (the rest is ignored and `index` says so in a warning). Chunk indexes start at 0. Chunking is deterministic, so `text_hash` of a chunk and the same text always give the same chunk set.

**D4. Store: one table, `embedding_chunks`** (migration `0005`). Columns: `id`, `project_id` (FK `projects.id` ON DELETE CASCADE), `source` (`chat`, `job` or `text`: the same three words are the tool's `source` argument and filter in every action), `chat_message_id` (FK `chat_messages.id` ON DELETE CASCADE, nullable), `research_job_id` (FK `research_jobs.id` ON DELETE CASCADE, nullable), `ref` (`c:<message id>`, `j:<job id>` or `t:<key>`, the identity of the source item), `chunk_index`, `text`, `text_hash` (SHA-256 hex of the chunk text), `model`, `dimensions`, `encoding`, `vector` (BLOB), `created_at`. A check constraint ties `source` to which of the two foreign keys is set. Unique `(project_id, ref, chunk_index, model, dimensions, encoding)` (a computed `ref` string, not the nullable keys, because SQLite treats NULLs in a unique index as distinct). Indexes on `(project_id, model, dimensions, encoding)` and on `(project_id, source)`, and PARTIAL indexes on `chat_message_id` (where not null) and `research_job_id` (where not null) so that the cascade of a deleted message, job or chat does not scan the table once per parent row inside one write unit (SQLite runs `DELETE ... WHERE chat_message_id = ?` per deleted parent). The check constraint and the unique constraint are NAMED (`ck_embedding_chunks_source_keys`, `uq_embedding_chunks_item`) so the ORM-versus-schema test compares them. `chat_messages` has no AUTOINCREMENT, so a message id can be reused after its newest messages are deleted; that is safe only because the cascade deletes the old message's chunks in the same statement (foreign keys are on for every connection, the sync migration engine included), and a test pins it. The chunk text is stored with its vector so a search result needs no join and survives a source edit; the foreign keys make deleting a chat, a research job or a project delete its vectors by cascade, which is how "removes its vectors" holds without a second delete path. `delete_project` finds the table by introspection (it references `projects` with CASCADE only; the other two keys point at tables that are themselves scoped, two hops away). The `retained table` rules do not apply (the table keeps nothing past its project). The downgrade drops the table.

**D5. Which items `index` embeds.** `chat`: every message of the project's chats with non-blank text (both roles). `job`: every research job of the project whose status is `completed` with non-blank `result_text` (an `incomplete` run has no answer, per the jobs tool). `text`: the `items` the caller passes (`[{"key", "text"}]`, 1 to 100 items, key non-blank at most 128 characters, text non-blank at most 100000 characters; a repeated key in one call is refused). An item is **pending** when it has no stored chunk for the call's `(model, dimensions, encoding)` or its chunks' `text_hash` no longer matches the current text (a job's result can change only when it first completes, a text key can be re-sent with new text). Re-indexing an unchanged item embeds nothing and spends nothing. `status` reports items with NO chunk for the triple as not indexed and does not report changed items; one helper decides "non-blank text" for `index` and `status` alike. A changed item's old chunks for that triple are deleted in the same unit as its new ones are inserted.

**D6. `index` is bounded and resumable.** `limit` (default 256, 1 to 2048) stops the call after the whole item that makes the running count of new chunks reach `limit`, taking items in the store's order (oldest first): at least one whole item is always taken, so a loop on `remaining` always makes progress and a call embeds at most `limit` plus 49 chunks; `remaining` says how many pending chunks are left, so a caller loops until 0. The stored-chunk cap per project and `(model, dimensions, encoding)` is 20000 (our cap: it bounds the in-memory search at about 80 MB of float32 at 1024 dimensions and 205 MB at 2560); an `index` that would exceed it fails `invalid_request` before any call, saying to delete something. Chunks are embedded in batches of at most 64 inputs AND at most 100000 characters in total (the character budget keeps a batch under the API's 120000-token request limit for dense text such as CJK or code, where a token can be one character; the 64 by 4000 shape was only 42550 tokens for the compressible English of `embeddings_64_inputs_4000_chars`), each batch one upstream request through `costed_call` followed by that batch's own write unit, so a failure on batch 3 keeps the work of batches 1 and 2 and the spend of all three is recorded. The planner packs chunks in order; an item (at most 50 chunks) may span two batches, and is written when the batch holding its last chunk is written, so an item whose batches did not all complete stores nothing and stays pending. A 400 for a batch is surfaced as `invalid_request` with the stored count; the character budget is what keeps a legitimate batch from being refused.

**D7. The order inside a batch** follows the recorder contract: resolve and commit the project (through `costed_call`), upstream call holding no write unit, record the event, THEN the batch's write unit wrapped in `agent.shielded_write` (it follows a billed call). The write is "write what still exists": inside the unit it looks the project up by NAME (it may have been deleted and recreated while the call ran, since `costed_call` resolves the project before every batch) and inserts each chunk only when its source row still exists and belongs to that project (`INSERT ... SELECT ... WHERE EXISTS` for `chat` and `job`), so a chat, job or project deleted during the billed call skips those items (counted as `skipped_items` with a warning) instead of failing the foreign key and masking as `internal_error`. One in-process lock per project name (the `JobLocks` pattern, a new `embed_locks` in `AppContext`) is held by `index` and `delete`, so two concurrent `index` calls on one project do not both embed the same pending items; `search` and `status` take no lock. The write inserts all rows of the batch in one unit (`INSERT ... ON CONFLICT DO NOTHING ... RETURNING id` on the unique key, so the counts come from the rows actually inserted), so a repeat after a cancelled write does not double-store. A decode failure of a billed response (a vector of the wrong length) is `unexpected_response` raised AFTER the event is recorded; nothing of that batch is stored.

**D8. Decoding.** `int8`: base64 to exactly `dimensions` bytes. `binary`: base64 to exactly `dimensions / 8` bytes. The stored vector is those bytes unchanged. Validation is strict (invalid base64, a wrong length, `index` outside the batch or repeated, a `data` count different from the inputs) and raises `unexpected_response`. Evidence: the recorded vectors all decode to the exact sizes (`embeddings_single_06b` 1024, `embeddings_two_4b_dim256` 256 each, `embeddings_binary_06b` 32 each, `embeddings_4b_default_dims` 2560).

**D9. Search.** One upstream request embeds the query (same model, dimensions, encoding as the index being searched; defaults identical to `index`). Candidates are the project's chunks with that triple, optionally filtered by `source`. `int8`: the query and every stored vector are read as `int8`, cast to float32, and the score is cosine similarity (a zero vector scores 0). `binary`: the vectors are unpacked to bits and the score is `1 - hamming / dimensions`. The top `top_k` (1 to 20, default 5) chunks with a score at or above `min_score` (default none) are returned, best first, ties broken by chunk id; each hit carries `score`, `source`, the source reference (`chat_id` and `message_id`, `job_id`, or `key`), `chunk_index`, and the chunk `text` cut to 800 characters. No vector, no hash and no raw bytes are ever returned. With no stored chunks for the triple it returns zero hits with a warning (not an error) and makes NO upstream call (nothing to compare against, so no spend). The scan loads only `id` and `vector` of the candidates (never the chunk text), scores them in blocks of 2048 rows under `asyncio.to_thread` (so the event loop is not blocked), keeps the top `top_k` per block and merges them, breaking ties by chunk id (`numpy.lexsort`), and then loads the text and the source reference (including `chat_id`, by a join on `chat_message_id`) for the winning chunks only. There is no cache and `N` is at most 20000. `binary` scoring uses a 256-entry popcount table over the XOR of the packed bytes, and its scores are 0 to 1, so a negative `min_score` is meaningful for `int8` only.

**D10. Cost.** The response reports `usage.cost.total_cost` in USD as a float (`8e-09` for 2 tokens on the 0.6b model; `3.6e-07` for 12 tokens on the 4b model: 4 and 30 nano-USD per token, equal to the documented prices in `pricing.EMBEDDINGS_NANO_PER_TOKEN`). `usage_from_embeddings_response(usage)` parses it with `to_nano` (source `reported`) only when `cost.currency` is `USD` (a non-USD cost is unknown, source `none`, like the Agent parser and the main `usage-recording` "Unusable cost"), `prompt_tokens` and `total_tokens` with `to_tokens`, keeps the whole object as `raw`, never raises, and is registered in `usage._PARSERS` for `embeddings`; the tool itself passes a parsed `Usage` (the registry entry serves a caller that passes the raw mapping to `record_usage`). `embeddings_usage(model, raw)` is the one rule the tool uses: the parsed usage when its source is `reported`; else, when `prompt_tokens` is a valid count and the model is priced, `computed_usage(pricing.embeddings_cost_nano(model, tokens), ...)`; else unknown (source `none`, never zero). "Reported wins": a reported cost is never replaced by the computed one.

**D11. Recording.** `run_embed` is the pure caller of `costed_call` (`call` is `client.embed(body)`, the interpreter returns `Recording("ok", embeddings_usage(...), model-when-a-string, None, None)`), so the sweep of `costed_call` callers gains it (four callers). The event: tool `perplexity_embed`, API `embeddings`, the response `model`, no preset, request id null (the body has none; the header is not exposed by the client), the project name, the token counts and the cost. A search or an index batch each record one event; `status`, `delete` and a search with nothing to compare against record none.

**D12. Result of `index`.** `embedded_chunks`, `embedded_items`, `skipped_items` (already current), `remaining` (pending chunks not embedded because of `limit`), `requests` (upstream requests made), `input_tokens`, `cost_usd` (the exact sum of the recorded costs of this call's requests), `cost_source` (`reported`, `computed`, `mixed` or `none`: `none` when no request had a known cost), `calls_cost_unknown`, `latency_ms`, `project`, `warnings`. A failure on a later batch raises the error AFTER the earlier batches were stored and recorded; the error message says how many chunks were stored first.

**D13. Errors.** Every validation failure of the API is HTTP 400 `{"error": {message, type, code}}` (the documented 422 does not occur) and maps to `invalid_request`; 401 `authentication`; the existing status mapping and `Retry-After` handling apply; a 429 body was not captured. One probed message is wrapped (`failed to get embeddings: POST /v1/embeddings: 400 Bad Request: {...}` for a bad dimension): it passes through redacted like any message.

**D14. Privacy of vectors and text.** Vectors are never put in a result, a log record or an error, and the base64 strings of a response are never logged (the client logs method, path, status and request id only). Chunk text is stored (the caller's own content); the configured API key is scrubbed from hit text on the way out (`scrub_secrets`) and a `pplx-` shaped example is kept. The tool description and the README say that `index` sends chunk text to Perplexity.

**D15. Tests.** Offline through `build_server` with a `MockTransport` serving the recorded fixtures. Vector-math tests use small hand-built vectors with known cosine and Hamming values (the recorded vectors serve for decode, sizes and recording, not for ranking). A migration test follows `tests/test_jobs_migration.py` (up, down, the ORM model compared with the migrated schema, head moves to `0005`), plus a cascade test (deleting a chat, a job and a project removes its chunks), plus the mutation-check rule for the recording order and for the shielded write. Lessons applied: `redaction-patterns-need-identifier-regressions` (a `pplx-embed-v1-0.6b` id in text), `best-effort-writers-and-the-callers-write-lock`, `framework-logs-carry-bound-parameters` (texts, queries, vectors never reach a log), `dedupe-index-only-covers-the-statuses-it-names` (null request ids: no dedupe, each request billed).

## Risks / Trade-offs

- **Chunk text leaves the machine on `index`** (D14) -> said in the description and README; only the caller's explicit `index` does it.
- **A billed batch whose write fails** (D7) -> the event is recorded, the batch is re-embeddable (nothing stored, so the item is still pending) and the retry is billed again; documented.
- **Memory and blocking of search** (D9) -> at most 20000 chunks per triple (about 80 MB of float32 at 1024 dimensions, 205 MB at 2560, scored in 2048-row blocks off the event loop), ids and vectors only are loaded, no cache.
- **Cosine on `int8`** is the provider's recommended reading of its quantized vectors; its quality is the provider's.
- **numpy is a new dependency** (about 20 MB; floor `numpy>=2.3.2`, the first release with cp314 wheels, because CI runs 3.12 and 3.14; imported lazily inside the scoring functions because it costs 100 ms or more at import) -> pinned in `uv.lock`; CI builds with `--locked`.
- **A stale vector after the model changes** -> vectors are keyed by `(model, dimensions, encoding)` and a search only compares equal triples; `status` lists every triple; `delete` can drop a triple.
- **Ten tools** (D1) -> measured in group 4; one tool with four actions is the lean option.
- **The 429 body and the real-world rate limit are unobserved** -> generic handling, `index` batches run one after the other, never concurrently.
- **A reported cost the parser cannot read** -> `computed`, else `none`; counted by `calls_cost_unknown`.
- **Deleting a chat deletes its vectors silently** (D4) -> by design; `status` shows the counts. `delete_project` visits tables in introspection order, so `chats` is deleted first and its chunks go by cascade (uncounted) while job and text chunks are still present when `embedding_chunks` is deleted (counted); a test pins this outcome.
- **A source deleted while a batch is in flight** (D7) -> written around, reported as skipped, billed once.
- **A 400 for a batch** -> surfaced with the stored count; the character budget prevents it for legitimate content.

## Migration Plan

`0005` creates `embedding_chunks`; the runner backs up `backup-0004.db` first and upgrades in one transaction; the downgrade drops the table (vectors are lost, the source chats and jobs are untouched, and `index` rebuilds them). pm2 restart applies it.
